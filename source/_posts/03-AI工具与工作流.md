# 你怎么理解 AI

## 问题

“说说你对 AI 的理解。”

## 我的回答

我直接讲自己怎么用 AI：从需求文档到调研、开发、审查、测试、CI/CD 的一套流程，并说这套流程沉淀成了 skill。回答偏“使用经验”，没有讲能力边界。

## 参考答案

分三层讲：

- 能力：模型擅长生成、归纳、改写、代码初稿、日志初筛、方案对比；本质是条件生成，给定上下文续写最可能的内容。
- 边界：会编事实、上下文有限、跨会话不一致、不能处理涉密数据、不能为结果负责。
- 方法：人负责决策与验证，模型负责执行与初筛；关键结论回官方文档或源码核对。

## 相关知识点

### 模型是什么

模型是条件生成器：给定一段上下文，它按概率续写。它没有事实数据库，也没有真正的推理保证。看起来像推理的过程，是训练数据里学到的模式在起作用。

这解释了几件事：

- 为什么同一个问题换一种问法，答案会不同。
- 为什么它会把不存在的 API 说得像真的。
- 为什么它需要“一步步想”这类提示才更稳。

### 能力与边界

| 维度 | 能做 | 不能做 |
|---|---|---|
| 生成 | 初稿、改写、翻译、代码 | 保证事实正确 |
| 归纳 | 长文摘要、日志初筛、方案对比 | 保证不遗漏关键信息 |
| 推理 | 结构化分析、假设生成 | 承担决策责任 |
| 上下文 | 单次长文本 | 跨会话记忆、超长上下文稳定 |

### 为什么“会用”不等于“理解”

会用工具的人，知道在什么场景下用什么工具；理解工具的人，还知道工具什么时候会失效。

面试里只讲“我会用 Cursor 写代码”，和讲“我知道它会在跨文件重构时丢约束，所以会分模块给验收标准”，是两个层次。


### 训练与推理的区别

模型的能力来自训练，回答发生在推理：

- 训练是把大量文本压缩进参数，学的是分布与模式。
- 推理是给定上下文，按参数预测下一个 token。
- 模型没有“查数据库”的动作，除非显式调用工具。

这解释了为什么它会把相似的东西混在一起，也解释了为什么“让它再想想”有时有用、有时没用：它没有真正的记忆，只是在重新采样。

### 温度与采样

同一个提示，输出可能不同，因为采样有随机性：

- 温度低，输出更确定、更保守。
- 温度高，输出更多样、更容易跑偏。

写代码、做事实问答适合低温度；头脑风暴、文案适合高温度。这个参数不改变模型知道什么，只改变它怎么选。

### 上下文窗口

上下文窗口是模型一次能看的 token 上限。超过上限，前面的内容会被截断或压缩。

实际影响：

- 长日志、大文件不能一次塞进去。
- 多轮对话到后面，早期约束可能被挤掉。
- 跨文件任务要分块，不能指望模型记住所有细节。

# 你常用哪些 AI 工具

## 问题

“说一下你常用的 AI 工具。”

## 我的回答

我讲了工具演进：Cursor、Claude Code 与 Codex、Hermes、DSH。讲 DSH 的插件化设计，提到自己写过插件管理器。回答不错，但没有讲“为什么换”和“什么场景用哪个”。

## 参考答案

按任务选工具，而不是按新旧：

- 局部补全与小改写：编辑器内的补全工具。
- 跨文件任务：能读仓库、跑命令、多文件修改的 agent。
- 长任务与多入口：带记忆与会话管理的工具。
- 自定义工作流：插件化、可换模型、可扩展工具的运行环境。

换工具的原因通常是约束，不是新鲜感：模型单一、工作流固定、扩展困难、成本不可控。

## 相关知识点

### 工具形态

| 形态 | 能力 | 局限 |
|---|---|---|
| 补全 | 编辑器内预测下一段 | 跨文件能力弱 |
| 对话 | 问答、生成、改写 | 不能直接操作仓库 |
| Agent | 读文件、跑命令、改代码、循环 | 需要权限与验证 |
| 运行环境 | 插件、多模型、工具扩展 | 配置与维护成本 |

### 插件化的意义

插件化把“模型、工具、界面”解耦：

- 换模型不用改工作流。
- 加工具不用改核心。
- 团队可以按需裁剪。

代价是复杂度：版本兼容、依赖冲突、状态管理。我写过插件管理器，踩过这些坑，对“能跑”和“能用”的区别有具体体会。

### 场景匹配

- 写一个函数：补全最快。
- 重构十个文件：agent 更合适。
- 查一个 API 的用法：对话加官方文档。
- 跑一条固定流程：技能包或脚本。

工具没有绝对优劣，匹配任务才有意义。


### 成本与隐私

选工具不只看能力，还要看成本与隐私：

- 成本：按 token 计费，长上下文、多轮调用会放大开销。
- 延迟：本地模型快但能力弱，云端模型强但有网络延迟。
- 隐私：代码、日志、客户数据能不能出内网。
- 可控性：能不能换模型、能不能审计调用。

企业环境里，隐私与可控性常常比能力更重要。

### 工具的组合

一个任务可能用多个工具：

- 用 agent 读仓库、改代码。
- 用对话工具查文档、解释报错。
- 用脚本做批量处理与校验。
- 用本地模型处理敏感文本。

组合的原则是“每个工具做它擅长的事”，不是找一个万能工具。

# 你的工作流是什么

## 问题

“你说把工作流沉淀成了 skill，具体是什么流程？”

## 我的回答

我说了大概：需求文档、调研、开发、审查、测试、CI。但没有给出具体的阶段划分与产物，也没有说明每个阶段的输入输出。

## 参考答案

我的工作流是 dw 技能包，分三个阶段：

- dw-plan：质询需求，冻结 SPEC。
- dw-execute：按 SPEC 在隔离子会话里执行，回传执行回执。
- dw-review：对照 SPEC 逐条验收，输出评审报告。

每个阶段都有明确的输入、产物和退出条件，避免“边想边写”。

## 相关知识点

### dw-plan：把模糊需求变成可执行规格

流程：

1. 询问是否有参考文档（PRD、技术方案、竞品分析）。
2. 调用 grill 技能质询需求：边界、用户故事、验收条件、技术约束、非功能需求。
3. 调用 to-spec 产出 `SPEC.md`，末尾带 `SPEC READY` 块。

`SPEC READY` 块包含：完成标准、仓库路径、基线、测试 seam、非目标、外部权限、下一步路由。它的作用是让执行阶段不需要再问“到底要做什么”。

### dw-execute：隔离执行

读取 `SPEC.md`，确认 `SPEC READY` 完整，然后用 `subagent_fork` 创建隔离子会话执行：

- 子会话有独立上下文，不污染主会话。
- 子会话有完整工具链，可以读代码、跑测试。
- 子会话完成后回传执行回执（改了什么、测试结果、遗留问题）。

隔离的好处是长任务不占主会话上下文，坏处是要设计好交接信息，否则子会话会重复问。

### dw-review：对照验收

读取 `SPEC.md` 的验收条件与执行回执，逐条检查：

- 找到代码变更证据。
- 验证行为是否符合规格。
- 标记通过、失败、不适用。

再调用代码审查技能，检查约定、安全、性能、测试覆盖。最后给出合并建议：通过、要求修改、阻塞。

### 为什么要有退出条件

没有退出条件的工作流，会停在“感觉差不多了”。有了 SPEC 与回执，每个阶段都有可检查的产物：

- 规划阶段的产物是 SPEC。
- 执行阶段的产物是回执与代码。
- 评审阶段的产物是报告与结论。

这也是面试时可以讲的重点：不是“我会用 AI”，而是“我能把 AI 放进一个有验收标准的流程”。


### SPEC READY 的样子

规划阶段的产物是一个可检查的块：

```text
SPEC READY

- Status: ready for implementation
- Source: <SPEC.md 路径>
- Repository: <仓库路径>
- Baseline: <当前分支或提交>
- Test seam: <验收用的行为接缝>
- Non-goals: <明确不做的内容>
- External authority: <提交、推送、评审、部署权限>
- Next route: dw-execute
```

这个块的作用是让执行阶段不用再问“做什么、做到什么程度、能不能提交”。

### 阶段的失败模式

| 阶段 | 常见失败 | 后果 |
|---|---|---|
| plan | 需求没问清就写 SPEC | 执行阶段反复返工 |
| plan | 验收条件不可测 | 评审时扯皮 |
| execute | 子会话缺上下文 | 重复问、做错方向 |
| execute | 没有测试 seam | 改完不知道对不对 |
| review | 只跑测试不对照 SPEC | 功能对但需求没满足 |
| review | 审查只看风格 | 漏掉安全与性能问题 |

工作流的价值不是“看起来专业”，是提前暴露这些失败。

### 为什么用子会话执行

长任务放在主会话里，会占满上下文，后面的讨论质量下降。子会话隔离后：

- 主会话保留决策与讨论。
- 子会话专心实现与测试。
- 交接靠 SPEC 与回执，减少口头同步。

代价是交接信息要写清楚，否则子会话会重新问一遍。

### 远程入口：QQ 机器人

本机用 agent 有一个限制：人必须坐在电脑前。我把 Hermes 和 DSH 接到 QQ 机器人上，用消息作为入口，解决三件事：

- 多端查看：手机、平板、电脑都能看到同一个任务的进度。
- 继续对话：不在电脑前时，接着上一轮继续聊，不必重新交代上下文。
- 异步反馈：长任务跑完，摘要推回 QQ，不用一直盯终端。

接入方式是 QQ 官方机器人开放平台。DSH 侧用 `@tencent-connect/dsh-qqbot` 插件，配置在单独的 qqbot profile 里；Hermes 也接了自己的入口。官方平台用 Webhook 回调，所以还需要一个能接收事件的 HTTP 服务。

这部分我单独写了 qqbot 项目：

- Python 3.12，标准库 `http.server`，nginx 反代到本地端口。
- 入站用 ed25519 验签，防伪造事件；`msg_id` 去重，防重复投递。
- 滑动窗口频控与日配额，防止刷接口。
- 白名单指令分发，聊天与音乐功能转发到本地 API，LLM 走 ai-gateway。
- 内置 MC 服务器监控（状态、TPS、内存、日志、备份）。

这个项目的价值不在功能多，而在它把“消息入口”这件事做成了可运维的服务：验签、去重、限流、配额、日志，都是生产环境要考虑的。

和 dw 工作流结合后，链路是：QQ 发需求，agent 走 plan 产出 SPEC，execute 在隔离子会话执行，review 回传结论，摘要推回 QQ。人只需要在关键决策点介入。

# skill 和提示词差在哪

## 问题

“说一下你怎么理解 skill 和提示词。”

## 我的回答

我只说了“用 @ 引用 skill，模型会读对应的 md 文件，而不是把内容粘贴进输入框”。没有讲 description、自动触发，也没有讲提示词工程。

## 参考答案

- 提示词是单次任务的指令：告诉模型这次要做什么、有什么约束、输出什么格式。
- skill 是可复用的流程包：包含指令、参考资源、脚本，还有 description。description 决定模型在什么场景下自动加载它，@ 引用是手动触发。

提示词解决“这一次怎么做”，skill 解决“这一类事怎么做”。

## 相关知识点

### SKILL.md 的结构

一个技能通常包含：

- 元信息：name、description、是否允许自动调用。
- 流程：步骤、输入输出、退出条件。
- 资源：参考文档、模板、脚本。
- 约束：什么时候用、什么时候不用、常见错误。

description 很关键。模型靠它判断“当前任务是否匹配这个技能”。写得太泛，技能会被滥用；写得太窄，该触发时不触发。

### 各工具怎么触发技能

不同工具的触发机制不一样，差别在“描述什么时候进上下文、正文什么时候加载”。

| 工具 | 描述注入 | 正文加载 | 显式调用 |
|---|---|---|---|
| DSH | 会话首次请求前注入技能目录：名称加截断描述（默认上限 500 字符） | 模型调用 `skill` 工具加载完整指令 | 用户 `/name` 直接注入 |
| Hermes | 系统提示里包含技能索引（名称、描述、分类，约 3k tokens） | `skill_view` 按需加载全文与引用文件 | 斜杠命令 `/name` |
| Codex | 技能列表与 `SKILL.md` 的 description 作为触发信号 | 命中后加载 `SKILL.md` 正文 | `$name` 或明确任务匹配 |

所以“首轮加载全量描述”对 DSH 与 Hermes 基本成立，对 Codex 是以 description 作为触发信号：

- DSH 在首轮把技能目录作为持久消息注入，描述被截断到 500 字符，避免目录占满上下文；目录会随技能增删更新。
- Hermes 把技能索引放进系统提示，正文用渐进披露：先看索引，需要时 `skill_view` 加载全文，再需要时加载引用文件。索引约 3k tokens。
- Codex 把 `SKILL.md` 的 description 当作主要触发信号，技能可以自动触发；自动触发不能按单次请求跳过，这是它的已知取舍。

### 三个例子

例子一：DSH 的技能目录。

会话开始时，系统提示里出现 `available_skills` 列表，每个技能一行名称加一句描述。模型看到“grilling：把模糊需求质询成可执行规格”这样的描述，在需求分析时调用 `skill` 工具加载全文。描述截断到 500 字符，目录不会失控。

例子二：Hermes 的渐进披露。

Hermes 首轮给出技能索引（`skills_list` 的形态，名称、描述、分类），模型判断需要某个技能后调用 `skill_view` 拿全文；如果技能里有 `references/`，再按需读取具体文件。这样索引只占少量 token，正文与资料按需付费。

例子三：Codex 的自动触发。

用户在 Codex 里说“帮我审一下这个分支”，描述里含“code review”的技能被匹配，自动加载并执行。代价是简单任务也可能触发重流程，社区有“跳过自动触发”的诉求。

### 预加载的取舍

- 预加载全量描述：模型知道有什么技能，但目录占上下文，描述还要截断。
- 按需加载：上下文干净，但依赖模型判断或用户点名。
- 预加载常用技能：折中，需要维护“常用”清单。

没有统一答案，取决于技能数量、任务类型与上下文预算。

### 技能与提示词的分工

| 维度 | 提示词 | 技能 |
|---|---|---|
| 粒度 | 单次任务 | 一类流程 |
| 复用 | 复制粘贴或模板 | 文件引用 |
| 触发 | 每次输入 | 自动或手动 |
| 维护 | 版本管理 | 版本管理 + 依赖 |

复杂任务应该拆成技能，而不是堆一个很长的提示词。长提示词的约束会互相冲突，模型顾此失彼。

### 技能不是万能

技能也有边界：

- 技能依赖模型能力，模型弱，流程再细也会走偏。
- 技能需要维护，流程变了、工具变了，技能要跟着改。
- 技能不能替代验证，输出仍要人检查。


### 一个 SKILL.md 的骨架

```markdown
---
name: example-skill
description: "一句话说明这个技能做什么、什么时候用。"
disable-model-invocation: true
---

# example-skill

## 适用
- 什么时候用
- 什么时候不用

## 流程
1. 输入是什么
2. 做哪些步骤
3. 输出什么
4. 退出条件

## 资源
- 参考文档
- 模板
- 脚本

## 常见错误
- 容易踩的坑
```

`description` 决定自动触发，流程决定执行质量，资源决定可复用性。

### description 怎么写

- 写“做什么”，不写“很重要”。
- 写“什么时候用”，让模型能匹配场景。
- 写“什么时候不用”，减少误触发。
- 一句话能说清，不要堆关键词。

不好的 description：“一个强大的、全面的、专业的技能。”

好的 description：“把模糊需求质询成可执行规格，适用于需求分析阶段，不适用于已有明确规格的实现任务。”

### 技能的维护

技能会过期：

- 工具换了，命令要改。
- 流程变了，步骤要改。
- 模型变了，提示要调。

维护成本是技能化的代价，所以不要为一次性任务建技能。

# 提示词工程怎么做

## 问题

“你怎么写提示词？有没有做过提示词优化？”

## 我的回答

我说提示词就是输入框里的话，没有展开怎么写好，也没有讲提示词工程的方法。这是面试里比较明显的缺口。

## 参考答案

提示词工程不是“把话写长”，是把任务写清楚、可验证、可迭代。

一个任务描述可以拆成六段：

- 角色：模型扮演谁。
- 背景：前因、上下文、素材在哪。
- 目标：要达成什么。
- 约束：不能做什么、边界在哪。
- 输出格式：列表、JSON、代码、表格。
- 验收标准：怎么算做对了。

不是每次都要写满六段，但目标、约束、验收几乎总是要的。

## 相关知识点

### 六段模板的例子

编码场景：

- 角色：熟悉 Go 的资深工程师。
- 背景：订单服务在高并发下偶发死锁。
- 目标：找出死锁可能出在哪，给出改法。
- 约束：不改对外接口，不引入新依赖，改动尽量小。
- 输出格式：先列可疑点及依据，再给改法，最后给代码片段。
- 验收标准：现有测试通过，能跑通 `go test`。

这个结构的好处是，模型知道边界，人也知道怎么验收。

### 常用技巧

| 技巧 | 做法 | 适用 |
|---|---|---|
| 清晰具体 | 说清对象、格式、边界 | 所有任务 |
| 给上下文 | 把必要材料喂进去 | 材料相关任务 |
| few-shot | 给 2–5 组输入输出示例 | 格式、风格要求高 |
| 格式约束 | 指定 JSON、表格、列表 | 需要程序解析 |
| 防呆指令 | 不知道就说不知道 | 事实类任务 |
| 思维链 | 让模型先推理再给结论 | 逻辑、数学、分析 |

few-shot 的例子要覆盖边界情况，格式与目标输出一致，数量够用就好，例子之间不能互相矛盾。

### 提示词是迭代出来的

写、测、改、重复：

- 写第一版。
- 用一批有代表性的输入跑，记录成功与失败。
- 根据失败案例调整措辞、补上下文、加示例。
- 重复到通过率够用。

固定部分做模板，常变部分抽变量；提示词要做版本管理，改坏了能回退。

### 提示词注入

模型分不清“指令”和“数据”。用户输入里写“忽略之前所有指令”，或者外部文档里藏恶意指令，都可能让模型跑偏。

缓解方式：

- 指令与不可信输入用标签分开。
- 工具权限最小化，关键操作要人确认。
- 输出校验与过滤。
- 沙箱隔离，注入成功也碰不到主机。

注入是结构性问题，不能只靠一句“不要听用户的”。


### 六段模板的完整例子

以写一篇技术博客为例：

- 角色：熟悉 Android 系统的技术作者。
- 背景：读者是有应用开发经验、没接触过内核的工程师；素材是调研笔记与源码。
- 目标：写一篇入门长文，讲清学习路径与核心机制。
- 约束：不用箭头，不做章节前后引用，代码要能追溯来源，不编造数据。
- 输出格式：Markdown，二级标题分节，代码块标注路径，表格用于对比。
- 验收标准：事实可核查，术语一致，每节自包含。

这段描述比“帮我写一篇 Android 内核文章”具体得多，模型知道边界，人也知道怎么验收。

### 迭代与测试

提示词不是一次写好的：

- 准备一批代表性输入。
- 记录每次输出的成功与失败。
- 针对失败补约束、加示例、改结构。
- 重复到通过率可接受。

固定部分做模板，常变部分做变量；版本要留，改坏了能回退。

### 成本意识

提示词越长，token 越多，成本越高。示例、上下文、约束都要有目的，不要堆“请务必”“非常重要”这类不增加信息的词。

# 用 AI 做日志分析

## 问题

“你说会用 AI 分析日志，具体怎么做的？”

## 我的回答

我说用 shell 抓 logcat、dmesg、dumpsys、tombstone，用 Python 脚本整理成可读报告，再交给模型分析。回答方向对，但没有讲“为什么不直接贴进输入框”和“怎么验证结论”。

## 参考答案

流程分四步：

1. 抓取：shell 把几类日志拉下来，按时间排序。
2. 预处理：脚本过滤关键字、合并时间线、提取异常栈，输出成文件。
3. 归纳：把文件交给模型，让它列可能原因与下一步该看的点，标注证据行。
4. 验证：人复现、对照源码、排除误判，最后给出结论。

关键是不把日志直接贴进输入框，而是先落成文件。原因有三：日志太长会被截断；输入框里混着指令与数据，模型容易把日志内容当指令；文件可以留存、可以分段、可以复核。

## 相关知识点

### 为什么不直接贴输入框

| 问题 | 后果 |
|---|---|
| 长度超限 | 日志被截断，关键行丢失 |
| 指令与数据混杂 | 日志里的文本可能被当成指令 |
| 无法复核 | 对话记录不便长期保存与对比 |
| 敏感信息 | 日志可能含路径、账号、密钥 |

落文件后，可以用脚本先做一轮过滤，减少 token，也方便把“结论对应哪几行”写清楚。

### 日志抓取

```bash
# 抓系统与崩溃日志
adb logcat -b all -d > logcat.txt
adb shell dmesg > dmesg.txt
adb shell dumpsys > dumpsys.txt
adb shell ls /data/tombstones/ > tombstones.txt
adb pull /data/tombstones ./tombstones/

# 抓指定进程
adb logcat --pid=$(adb shell pidof com.example.app) -d > app.txt
```

日志要带时间戳，最好同时记录设备版本、复现步骤、操作时间点，否则模型只能猜。

### 预处理

脚本做几件事：

- 按时间合并多个来源。
- 过滤无关 tag，只留错误、警告、崩溃、关键状态。
- 提取异常栈与前后若干行。
- 统计错误类型与出现次数。

预处理的目标是把“几万行”压到“几百行有用信息”，而不是让模型读全部。

### 提示与验证

给模型的提示要写清：

- 角色：熟悉 Android 系统的排障工程师。
- 背景：现象、复现步骤、设备版本。
- 任务：列可能原因，每条给出证据行与置信度。
- 约束：不确定就说不确定，不要编造根因。
- 输出格式：编号列表，每条含原因、证据、下一步验证。

模型给的是假设，不是结论。验证要靠复现、源码、实验。我曾经按模型给的假设查了半小时，最后发现它把一条正常的重连日志当成了崩溃原因。

### 留存

日志与结论要留存：

- 原始日志压缩存档。
- 预处理脚本与输出保留。
- 结论与验证过程写进复盘。

下次遇到相似问题，可以直接对比，而不是从零开始。


### 预处理脚本示例

```python
# 过滤与合并日志，输出给模型的文件
import re

KEEP = re.compile(r"(FATAL|ANR|Exception|error|failed|timeout)", re.I)

with open("logcat.txt", encoding="utf-8", errors="ignore") as f:
    lines = f.readlines()

out = [l for l in lines if KEEP.search(l)]
with open("logcat_filtered.txt", "w", encoding="utf-8") as f:
    f.writelines(out)
```

脚本只做机械过滤，不做判断。判断留给人和模型，但模型看到的是过滤后的文本。

### 给模型的提示模板

```text
角色：熟悉 Android 系统的排障工程师。
背景：应用在某版本后偶发 ANR，复现步骤见 steps.txt，日志见 logcat_filtered.txt。
任务：列出可能原因，每条给出证据行与置信度。
约束：不确定就标注不确定，不要编造根因。
输出：编号列表，每条含原因、证据、下一步验证。
```

这个模板把“输入、任务、约束、输出”分开，减少模型把日志内容当指令的风险。

### 验证清单

- 结论能否在日志里找到对应行。
- 假设能否用一次实验排除。
- 是否与已知版本行为矛盾。
- 是否漏掉更简单的解释。

# AI 做不好什么

## 问题

“你觉得 AI 有哪些局限？”

## 我的回答

我说 AI 会编、上下文有限、不能处理涉密数据。回答方向对，但太笼统，没有给具体场景与应对。

## 参考答案

按“会出错的地方”和“应对方式”讲：

- 事实会编：API、参数、版本行为。应对是回官方文档或源码核对。
- 上下文有限：跨文件重构会丢约束。应对是分模块、给验收标准、每步复核。
- 涉密数据不能给：公司代码、日志、客户信息。应对是本地模型或脱敏。
- 跨会话不一致：同一问题不同时间答案不同。应对是把关键结论写进文档。
- 不能负责：出了问题，责任在提交代码的人。应对是人做最终审查。

## 相关知识点

### 幻觉的常见形态

- 不存在的函数、参数、配置项。
- 版本行为记错，把新版本特性说成旧版本。
- 引用不存在的文档或论文。
- 把相似 API 的行为混淆。

应对方式不是“让它再确认一遍”，而是查官方文档、读源码、跑测试。

### 上下文与一致性

模型的上下文是有限的，跨文件任务容易出现：

- 前面定的约束后面忘了。
- 改了一个文件，另一个文件的接口没跟着改。
- 重复定义、命名冲突。

应对方式：

- 把任务拆小，每个任务给明确的输入输出。
- 用 SPEC 或清单固定约束。
- 每步做静态检查与测试。

### 涉密与合规

外部模型不适合处理：

- 公司源码与内部文档。
- 用户数据与日志。
- 密钥、证书、账号。

可行的替代：本地模型、脱敏后再问、只给最小必要信息。

### 责任边界

AI 可以写代码、写测试、写文档，但不能承担后果。代码合并前要人审查，线上出问题要人定位。把 AI 当“加速器”而不是“替代者”，是使用的前提。


### 幻觉的具体例子

- 让你用某个库的函数，函数名与参数看起来合理，实际不存在。
- 解释某个系统行为，把两个版本的特性混在一起。
- 引用一篇论文，标题与作者像真的，实际查不到。
- 给出一个配置项，文档里没有。

这些错误很难靠“再问一遍”发现，因为模型会用同样自信的语气重复。可靠的做法是查官方文档、读源码、跑最小实验。

### 上下文管理技巧

- 把关键约束写在最前面或最后面，中间容易被忽略。
- 长任务分块，每块给输入输出。
- 用文件承载上下文，而不是全部塞进对话。
- 每完成一步，把结论写进文档，下一轮从文档开始。

### 什么时候不该用 AI

- 需要承担法律或安全责任的判断。
- 没有可验证来源的事实。
- 涉密数据处理。
- 需要真实世界实验的结论。

# 面试再被问怎么答

## 问题

“如果重来一次，你会怎么回答‘你对 AI 的理解’？”

## 我的回答

当时只讲了用法。更好的答法是五段：

- 能力：生成、归纳、代码初稿、日志初筛。
- 边界：幻觉、上下文、涉密、不一致、责任。
- 方法：人决策、模型执行，关键结论回官方文档或源码核对。
- 案例：dw 工作流（plan/execute/review）、日志分析先落文件。
- 验证：能复现、能解释、能追溯到来源。

## 相关知识点

### 为什么这个结构有效

面试官问“理解”，想听的不是工具清单，而是判断力：

- 知道什么时候用，什么时候不用。
- 知道输出怎么验证。
- 知道出了问题怎么兜底。

五段结构把这三件事都覆盖了，而且每一段都能被追问。

### 可追问的点

- “你怎么保证模型不编？”回官方文档、源码、测试。
- “上下文不够怎么办？”拆任务、写 SPEC、分模块。
- “涉密数据怎么处理？”本地模型、脱敏、最小必要。
- “AI 写错了谁负责？”提交代码的人。

### 不要说的话

- “AI 什么都能做。”
- “我用 AI 写完了整个项目。”（经不起追问）
- “模型说的应该是对的。”
- 把设计参数说成实测结果。
