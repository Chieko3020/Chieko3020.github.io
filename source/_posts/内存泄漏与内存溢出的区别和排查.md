- 某次面试被问到：怎么区分内存泄漏和内存溢出，分别怎么排查。
- 当时只答了“泄漏是分配了没释放，溢出是申请得太多”，工具只说了 Valgrind，没有讲怎么用数据判断。这里补一份完整一点的记录。
- 约定：C++、Linux 用户态、glibc。

# 太长不看 ？

- 泄漏是“该释放的没释放”，看 RSS 或堆分配量随时间是否单调增长；溢出是“一次要得太多或写越界”，看失败点和边界。
- 先分清 VSS、RSS、PSS、USS，再看分配器缓存和碎片，避免把“RSS 不降”误判成泄漏。
- 泄漏定位用 ASan/LSan、Valgrind、heaptrack、gperftools、jemalloc profiling；溢出定位用 ASan/UBSan、core dump、OOM 日志。
- 泄漏可以很久不崩，溢出通常以 bad_alloc、SIGSEGV 或 OOM kill 结束。

# 三个词先分清

- 内存泄漏（memory leak）：分配出去的内存失去了引用，或者没有走释放路径，进程占用的内存随运行时间增加。
- 内存溢出（memory overflow）：申请的内存超过当前可用的上限，比如地址空间、cgroup 配额、物理内存加 swap；也可能指写入超过已分配边界，也就是缓冲区溢出。
- 内存越界（out-of-bounds）：读写超出分配范围。越界不一定会立刻崩溃，可能踩坏堆元数据，等到下一次 free 或 malloc 才 abort。

| 术语 | 本质 | 典型表现 | 常用工具 |
| --- | --- | --- | --- |
| 内存泄漏 | 该释放的没释放 | RSS 或堆分配量持续上升，最终 OOM | LSan、Valgrind、heaptrack、gperftools |
| 内存溢出 | 申请超过上限 | malloc 返回 NULL、new 抛 bad_alloc、被 OOM kill | 看返回值、cgroup 事件、dmesg |
| 缓冲区溢出 | 写入超过分配边界 | 栈破坏、堆元数据损坏、SIGSEGV 或 abort | ASan、UBSan、Valgrind、core dump |

- 面试里说“内存溢出”，多数时候指申请超过系统能给的上限。工程里说 overflow，往往指缓冲区越界。回答前先确认对方指哪一种，两种问题的排查路径完全不同。

# 内存指标先看对

| 指标 | 含义 | 什么时候看 |
| --- | --- | --- |
| VSS | 虚拟地址空间大小，包含已映射但未驻留的页和共享库 | 判断地址空间是否耗尽，不能直接当泄漏 |
| RSS | 常驻物理内存，包含共享库和 file-backed 页 | 最常用的泄漏观察指标 |
| PSS | 按共享比例分摊后的常驻内存 | 多进程比较，容器里更公平 |
| USS | 进程独占的常驻内存 | 想知道这个进程真正占了多少 |

```bash
ps -o pid,rss,vsz,pmem,comm -p <pid>
cat /proc/<pid>/status | grep -E 'VmSize|VmRSS|VmData|VmStk|Threads'
cat /proc/<pid>/smaps_rollup
pmap -x <pid> | tail -n 5
smem -P <name>
```

- `/proc/PID/smaps_rollup` 一次给出 Rss、Pss、Private_Clean、Private_Dirty、Anonymous、Swap 等汇总，比逐个 mapping 读省事。
- RSS 里有共享库和可回收的 file-backed 页，单看一个数会高估。判断泄漏时，配合 Anonymous 和 Private_Dirty 一起看。
- 容器里还要看 cgroup 的 `memory.current` 和 `memory.max`，进程自己看到的 RSS 不等于 cgroup 的总用量。

# 泄漏的判断：看曲线，不看绝对值

- 固定压测，记录 RSS 或堆分配量随时间的变化。泄漏的曲线通常单调上升，停止请求后也不回落；缓存和连接池会上升，但会稳定在一个水平。
- 重启后归零、运行一段时间后再次上升，基本可以确认和进程生命周期相关。
- 只看 RSS 容易误判。glibc 的 free 不一定把内存还给操作系统：brk 堆只有在顶部空闲时才能收缩，arena 和 tcache 会保留空闲块，碎片也会让 RSS 居高不下。
- `malloc_trim(0)` 可以尝试把空闲堆还给系统；`MALLOC_ARENA_MAX` 可以限制 arena 数量。两者都只能缓解分配器层面的占用，不能修复真正的泄漏。
- 业务层面常见的泄漏点：全局缓存没有上限、无界队列、连接或 fd 没有关闭、回调注册了没有注销、单例持有大对象、shared_ptr 循环引用。

```cpp
// 只增不减的全局缓存，是最常见的“泄漏”
std::unordered_map<std::string, std::string> g_cache;

void handle(const Request& req) {
    g_cache[req.key] = req.value;
}
```

- 这段代码不一定马上把内存耗尽，但请求量增大后会持续上升。加 LRU 上限、TTL 或定期清理，才算修复。

# 泄漏定位工具

| 工具 | 原理 | 典型用法 | 适用场景 | 代价 |
| --- | --- | --- | --- | --- |
| ASan/LSan | 编译期插桩，退出时做可达性扫描 | `-fsanitize=address`，`ASAN_OPTIONS=detect_leaks=1` | 能重编的开发和测试环境 | 内存占用明显增加，速度下降 |
| Valgrind Memcheck | 动态二进制插桩 | `--leak-check=full --show-leak-kinds=all` | 不能重编或想复现历史二进制 | 官方 Quick Start 给的数字是 20 到 30 倍减速 |
| Massif | 堆快照 | `--tool=massif`，`ms_print` | 看堆峰值和增长趋势 | 同样有明显减速 |
| heaptrack | LD_PRELOAD 拦截分配，记录调用栈 | `heaptrack ./app`，`heaptrack_gui` | 不想改编译参数，想看分配热点 | 有减速，需要符号 |
| gperftools | 替换分配器，定期 dump 堆 | `HEAPPROFILE=/tmp/heapprof ./app`，`pprof` | 已经在用 tcmalloc 的服务 | 需要链接 tcmalloc |
| jemalloc profiling | 分配器自带采样 | `MALLOC_CONF=prof:true`，`jeprof` | 已经在用 jemalloc 的服务 | 需要编译时开启 prof |
| bpftrace | 内核探针跟踪 malloc/free | uprobe 挂到 libc 的 malloc/free | 线上粗查，不能停进程 | 需要权限和符号 |
| malloc_info | glibc 导出 arena 统计 | `malloc_info(0, stderr)` | 判断 arena 和空闲块规模 | 只有 glibc 有 |

- 能重编就先上 ASan。它在 x86_64 Linux 上默认带 LSan，退出时打印泄漏栈；`detect_leaks=1` 可以显式打开。程序如果调用 `_exit` 直接退出，LSan 不会跑；常驻进程可以调 `__lsan_do_leak_check()`。
- 不能重编就用 heaptrack 或 Valgrind。heaptrack 通过 LD_PRELOAD 记录每次分配和释放，适合先看“谁分配得最多”；Valgrind 更全面，但慢，不要在生产环境长时间运行。
- 已经在用 tcmalloc 或 jemalloc 的服务，优先用它们自带的 heap profile，开销比 Valgrind 小。
- 线上不方便运行工具时，用 bpftrace 采样分配调用栈，或者先看 `malloc_info` 判断是不是 arena 或碎片的问题。

```bash
# ASan + LSan
g++ -std=c++20 -g -O1 -fno-omit-frame-pointer \
    -fsanitize=address,undefined app.cpp -o app
ASAN_OPTIONS=detect_leaks=1:abort_on_error=1 ./app

# Valgrind
valgrind --leak-check=full --show-leak-kinds=all \
         --track-origins=yes ./app

# heaptrack
heaptrack ./app
heaptrack_gui
```

- Valgrind 的输出会把泄漏分成 definitely lost、indirectly lost、possibly lost、still reachable。优先修 definitely lost 和 indirectly lost；still reachable 多数是全局对象或缓存，要结合业务判断。

# 溢出的判断

## 申请超过上限

- 32 位进程的用户空间常见是 3GB 左右，大块分配很容易失败；64 位地址空间大得多，但还会受 `RLIMIT_AS`、cgroup 配额、物理内存加 swap 的限制。
- Linux 默认允许 overcommit。`vm.overcommit_memory=0` 是启发式，`1` 总是允许，`2` 不允许超过 CommitLimit。允许 overcommit 时，malloc 可能成功，真正写页面时才触发 OOM。
- `malloc` 失败返回 NULL，`new` 失败抛 `std::bad_alloc`。不检查返回值就解引用，看到的就是 SIGSEGV。
- cgroup 的 OOM 看 `memory.events` 里的 oom 和 oom_kill；内核日志里通常有一行 “Killed process ...”，带上 total-vm、anon-rss、file-rss。
- `ulimit -v` 限制的是虚拟地址空间（RLIMIT_AS）；`ulimit -m` 在 Linux 上不强制生效，不能拿它当 RSS 上限。

```bash
cat /sys/fs/cgroup/<cgroup>/memory.current
cat /sys/fs/cgroup/<cgroup>/memory.max
cat /sys/fs/cgroup/<cgroup>/memory.events
dmesg -T | grep -i -E 'killed process|out of memory'
```

- 处理方式：检查每次分配的返回值，给 `new_handler` 一个明确的失败路径，给队列和缓存设上限，大对象改成流式处理或 mmap，入口做限流。

## 缓冲区越界

- 栈溢出：无限递归、在栈上放超大数组、线程栈设置得太小。结果是 SIGSEGV，core 里能看到很深的栈。
- 堆溢出：写超过 malloc 申请的长度，踩坏 chunk 头，可能在 free 时才 abort。
- 整数溢出导致分配过小：`count * size` 溢出后申请了一小块，随后按大长度写入。

```cpp
// 错误示例：长度来自外部输入，没有检查目标缓冲区大小
void copy_name(const char* src, size_t len) {
    char name[32];
    memcpy(name, src, len); // len 大于 32 时越界写栈
}
```

- ASan 会在 memcpy 处报 stack-buffer-overflow；没有 ASan 时可能踩坏返回地址，函数返回时才崩溃。
- 工具：ASan 查越界和 use-after-free，UBSan 查整数溢出和未定义行为，Valgrind 查非法读写；在开启优化并得到库支持时，`-D_FORTIFY_SOURCE=3`、`-fstack-protector-strong`、`-D_GLIBCXX_ASSERTIONS` 能拦住一部分。
- core dump：`ulimit -c unlimited`，确认 `/proc/sys/kernel/core_pattern`；用 systemd-coredump 时 `coredumpctl list`、`coredumpctl info PID`、`coredumpctl debug PID`。拿到 core 后用 `gdb ./app core` 看 `bt`、`info registers`、`x` 检查内存。

```bash
ulimit -c unlimited
cat /proc/sys/kernel/core_pattern
coredumpctl list
coredumpctl info <pid>
coredumpctl debug <pid>

gdb ./app core
(gdb) bt
(gdb) info registers
```

- 如果进程被 OOM killer 杀掉，通常没有 core，也没有 tombstone；要看 dmesg、cgroup 事件和系统日志。

# 泄漏和溢出的对照

| 维度 | 内存泄漏 | 内存溢出 |
| --- | --- | --- |
| 触发方式 | 长期累积，和请求量、运行时间相关 | 单次大申请或越界写，和输入大小、边界相关 |
| 内存曲线 | RSS 或堆分配量持续上升 | 突增，或者直接失败 |
| 是否崩溃 | 可能很久不崩，最终被 OOM 杀掉 | 常见 bad_alloc、SIGSEGV、abort |
| 第一现场 | 堆分配栈、缓存和容器 | 失败点、core、OOM 日志 |
| 主要工具 | LSan、Valgrind、heaptrack、gperftools | ASan、UBSan、core dump、dmesg |
| 修复方向 | RAII、上限、淘汰、弱引用 | 检查返回值、边界检查、限流、拆分大对象 |

- 两者也会一起出现：泄漏把内存吃到接近上限，下一次大申请就溢出；或者越界写破坏了分配器元数据，之后每次分配都失败。排查时不要只关注一个方向。

# 一份可执行的排查顺序

1. 量化现象：RSS、VSS、PSS、cgroup memory.current 的曲线，OOM 日志，core 有没有。
2. 判断类型：是持续上升、稳定水平、突增，还是直接失败。
3. 缩小范围：按请求类型、模块、线程拆分；二分版本；用开关关掉可疑功能。
4. 定位分配点：能重编就用 ASan/LSan；不能重编用 heaptrack 或 Valgrind；线上用 bpf 或分配器自带的 profile。
5. 修复：RAII、容器上限、背压、连接和 fd 的配对释放、循环引用打断。
6. 回归：长时间压测，观察 RSS 是否回到稳定水平；给 cgroup OOM 和 RSS 设告警。

# 修复和兜底

- 资源管理统一用 RAII。`std::unique_ptr`、`std::shared_ptr`、自定义 deleter 能把大部分手动释放路径消掉。
- 容器加容量上限：`std::vector` 用完 `clear` 后如果还要长期持有，考虑 `shrink_to_fit`；队列用有界队列，满了就阻塞或拒绝，不要无限堆。
- 缓存用 LRU 加 TTL，或者直接用有淘汰策略的组件；不要在业务代码里写只增不减的 map。
- 回调、信号、事件循环的注册和注销要配对；单例不要长期持有请求级对象。
- 大对象和频繁小块分配分开处理。对象池、mmap、流式解析都能降低峰值。
- 监控至少放 RSS、堆分配量、cgroup memory.events、OOM 次数。定期重启只能争取定位时间，不能替代修复。

# Android 上的对应工具

- `adb shell dumpsys meminfo PID` 看 PSS、Private Dirty、Native Heap、Dalvik Heap。
- `adb shell dumpsys meminfo -d PID` 带更多 ART 细节。
- `adb shell dumpsys procstats --hours 3` 看一段时间内的 PSS、USS、RSS 变化。
- native 代码同样可以用 ASan；Android 的 malloc debug 可以加 guard、填充和 backtrace，但需要改系统属性，适合调试版本。
- tombstone 只在 native crash 时生成；被 lowmemorykiller 或 OOM 杀掉通常没有 tombstone，要看 logcat 和系统日志。
- `adb shell am dumpheap` 导的是 Java 堆，不是 native 堆，不要拿它查 C++ 泄漏。
