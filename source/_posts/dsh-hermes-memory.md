# 写在前面

同时用两个 Agent 工具的人都会遇到一个问题：在 A 里学到的东西，B 完全不知道。

Hermes 有官方记忆机制，会话里记下的环境事实、踩过的坑、用户的偏好，会写进两个 markdown 文件，下次会话自动带回来。DSH 没有这套东西，每次开新会话都是白纸。于是同一件事要在两个工具里各说一遍，或者干脆只在一边用。

这个插件解决的是这一件事：让 DSH 读 Hermes 的记忆文件，并允许写回去。用了两个多月，记忆文件里现在有 22 条条目、归档了 34 次提交，DSH 侧累计调用写回工具 140 次。下面把统计数据、两个 harness 各自的记忆机制、插件实现和踩过的坑写清楚。

---

这篇的读者定位是同时用 DSH 与 Hermes 的人。如果只用其中一个，插件没有意义；如果两个都不用，前面的记忆机制部分可以当参考。

统计脚本与上一篇文章用的是同一套：解压 DSH 会话日志，抓 `tool/call` 里的工具名与参数，按会话去重。Windows 侧的数据通过 SSH 取回本机解析。日志路径与会话数在数据表里标注。

两个工具的使用方式差异很大。Hermes 接在聊天平台上，适合零散提问；DSH 是本地 Web UI，适合长时间写代码。同一份记忆在两边都能用，才不需要在切换工具时重新交代背景。

插件的另一个动机是审计。记忆写回会进 git，每一次修改都能查、能回滚。纯文本文件的这一层历史，比数据库里的记忆更容易检查和迁移。

# 先看数据

统计口径和上一篇文章一致：解析本地会话日志，按会话去重。

## 写回调用

| 来源 | `memory` 工具调用 | 有调用的会话 |
|---|---:|---:|
| Linux DSH | 113 | 35 |
| Windows DSH | 27 | 12 |
| 合计 | 140 | 47 |

按月分布：2026-09 四十次、2026-10 六十六次、2026-11 三十四次。

调用次数不能说明全部。模型判断「这段内容值得长期记住」才会调用，多数会话一次都不调，少数会话会连调好几次（比如一次性整理完一批环境事实）。

## 注入覆盖

| 指标 | 数值 |
|---|---:|
| 启用插件后的 DSH 会话 | 213（Linux 160 + Windows 53） |
| 每次会话注入的记忆条目 | MEMORY.md 13 条 + USER.md 9 条 |
| 注入位置 | system prompt 的 `hermes:memory` 段 |

注入没有「调用次数」这个概念，它在每次组装 prompt 时自动发生。213 个会话全部带记忆开局，这是插件的常态效果，比写回次数更能说明价值。

## 记忆本身的增长

| 指标 | 数值 |
|---|---:|
| 归档提交 | 34 次 |
| 提交时间分布 | 2026-09 十四次、2026-10 十一次、2026-11 九次 |
| 当前条目 | MEMORY.md 13 条、USER.md 9 条 |

归档提交的 message 是语义化的，比如「记录 DSH 技能发现需根级软链」「记录 chieko-skills 公网仓库与脱敏结构」。翻提交历史等于翻这两个月的技术踩坑记录。

一个有意思的数字：写回调用了 140 次，最终只沉淀成 22 条记忆。中间的大量调用是修改、压缩、合并，不是新增。这和下面要讲的 Hermes 记忆机制直接相关。

## 统计方法

三步：

- 遍历 `~/.dsh/sessions/*/*/session.v4.jsonl.zstd` 与 Windows 侧同名目录，`zstd -dc` 解压
- 每行按 JSON 解析，取 `type` 为 `tool/call`、`data.name` 为 `memory` 的记录
- 按会话目录去重，同一会话内多次调用只算一个会话

局限有三个：

- 只统计写回，注入没有调用动作，无法按次统计
- 插件是九月份装的，之前的会话没有注入，但日志里也不会有记忆相关记录
- Windows 与 Linux 的会话不重叠，可以相加；Hermes 两个源没有按技能记录，不参与这张表

## 记忆与上下文压缩的关系

上下文压缩会丢弃细节，记忆是压缩前的一次抢救机会。

Hermes 的 `flush_min_turns` 就是为这个设计的：压缩或退出前，如果本次会话已经聊了至少六轮，给模型一轮时间把值得留在长期记忆里的内容写进去。六轮以下是经验阈值，太短的会话通常没有可复用的结论。

这个机制解释了为什么 140 次写回只留下 22 条：压缩前的写入大多是「本次任务的临时结论」，过几天会被更好的条目替换掉。

# Hermes 的记忆机制

Hermes 的记忆是官方能力，配置在 `cli-config.yaml` 的 `memory:` 段。

## 两个存储

| 文件 | 内容 | 字符上限 | 约合 tokens |
|---|---|---:|---:|
| `MEMORY.md` | agent 自己的笔记：环境事实、约定、踩坑 | 2200 | 约 800 |
| `USER.md` | 用户画像：偏好、风格、期望 | 1375 | 约 500 |

两个文件在每次会话开始时拼进 system prompt。有字符上限这件事是关键设计，它决定了记忆的形态。

## 有界记忆与模型自查

配置注释里写得很直接：字符上限让记忆保持小而聚焦，agent 自己负责修剪，到达上限时必须合并或替换条目。

这带来两个后果：

- 记忆是**策展过的**，不是流水账。想记新东西，往往要先删掉或压缩旧的
- 记忆条目之间有竞争关系。两个月的使用里，140 次写回只留下 22 条，说明大量写入是替换与合并

## 两个触发时机

| 配置 | 默认值 | 作用 |
|---|---:|---|
| `nudge_interval` | 10 | 每十轮用户消息提醒一次「考虑保存记忆」 |
| `flush_min_turns` | 6 | 上下文丢失前（压缩、新会话、退出）给一轮保存机会，且本次会话至少六轮才触发 |

`nudge_interval` 解决「模型忘了记」，`flush_min_turns` 解决「上下文快没了才想起来」。两者配合，让记忆的写入不依赖模型的自觉。

## 插件生态

Hermes 的 `plugins/memory/` 下还有八套可选后端：`mem0`、`honcho`、`byterover`、`hindsight`、`holographic`、`openviking`、`supermemory`、`retaindb`。

这些插件替换的是存储与检索层，上面那两个 markdown 文件与字符上限的设计不变。多数人用不到，知道有这层扩展就够了。

---

## 条目长什么样

记忆文件不是自由文本，是 `§` 分隔的条目集合：

```markdown
§
主模型=custom:ai-gateway(4000)->deepseek-flash; 官方仅flash/v4-pro;
picker[v4-pro,flash](须移出_MODELS_DEV_PREFERRED)
§
DSH: 四模式,patch扁平-id,事故见dsh-deploy(P20 OOM;fix-dsh-tools勿砍);
技能=~/.agents/skills(根级软链=入口;包内新增须补软链)
```

每条尽量压缩，用分号与括号承载并列信息，虚词全省。这是字符上限逼出来的写法：2200 个字符要装下所有环境事实，只能牺牲可读性换取密度。

## 为什么用字符而不是 token

配置注释里给了一个换算：约 2.75 字符对应 1 token，且与模型无关。

用字符而不是 token 的理由是跨模型稳定。切换模型时 token 计量会变，字符数不会。代价是不够精确，但记忆的规模本来就不需要精确到 token。

## 记忆的写入审核

Hermes 的记忆不是想写就写。写入前有一层判断：

- 属于环境事实、约定、踩坑的，进 `MEMORY.md`
- 属于用户偏好、沟通风格、期望的，进 `USER.md`

写之前先查有没有同类条目，有就替换而不是新增。这一条在实际使用里最有价值：如果不去重，两次会话记下两条矛盾的环境事实，下次会话就会照着错的那条执行。

## 实际配置建议

默认值基本够用，可以按习惯调两处：

- 记忆增长太快：把 `memory_char_limit` 调小，逼模型更狠地压缩，淘汰低价值条目
- 觉得模型记不住事：把 `nudge_interval` 调小，提醒更频繁，代价是打断对话节奏

`flush_min_turns` 不建议调小，六轮是经验值，太小的会话没有值得记忆的内容。

# DSH 的记忆机制

DSH 没有原生记忆机制，这一点可以从主包的插件清单确认：bundles 里没有和记忆相关的插件，官方也没有对应能力。社区在 npm 上有若干第三方实现，比如 `@jacklika/dsh-memory`、`dsh-memory-core` 这一类，各自定义存储与注入方式。

DSH 提供的是扩展点。写一个记忆插件需要两个能力：

- 往 system prompt 里注入固定文本
- 注册一个工具，让模型能修改这份文本

两个扩展点对应两个服务：

| 服务 | 用途 | 服务键 |
|---|---|---|
| system prompt | 注入只读段落 | `systemPrompt` |
| tools | 注册可调用工具 | `tools` |

插件通过 `inject` 数组声明依赖的服务键，通过 `ctx.systemPrompt.section()` 注册段落，通过 `ctx.tools.register()` 注册工具。

## 为什么选择复用 Hermes 记忆

社区已有现成的 DSH 记忆插件，自己再写一个的理由只有一个：复用已有的记忆文件。

- 记忆已经在 Hermes 里积累了两个多月，重新建一套等于从零开始
- 两个工具共用一份记忆，换工具不丢上下文
- 复用 markdown 文件意味着记忆可以直接编辑、可以用 git 管理、可以进备份

代价是记忆的格式与策展逻辑要跟 Hermes 保持一致，不能自由设计。

---

## 插件如何挂载

DSH 的插件通过 profile 的依赖与 bundle 声明挂载：

```json
// ~/.dsh/profiles/<profile>/package.json
{
  "dependencies": { "插件名": "file:本地路径或版本号" },
  "dsh": { "profile": { "bundles": ["插件名"] } }
}
```

插件包内部用 `cordis.patch.yml` 描述插入的行，启动时按顺序加载。这个机制对插件作者的要求是：插件必须能独立完成「读文件、注册段、注册工具」三件事，不能依赖宿主提供的记忆接口。

## 服务注册的约定

Cordis 的插件通过 `inject` 声明依赖的服务键，服务提供方用 `super(ctx, "<key>")` 注册。两边字符串必须完全一致，否则访问时抛错。

这套设计的好处是依赖显式：插件能用哪些服务，写在 `inject` 数组里一目了然。代价是没有编译期检查，拼错服务名要到运行时才暴露。

## 社区方案的位置

社区插件的典型做法是自建存储与注入：

| 方案 | 存储 | 注入方式 |
|---|---|---|
| 社区记忆插件 | 自有数据库或文件 | 各自的 system prompt 段 |
| 本插件 | 复用 Hermes 的 markdown | 单个只读段 |

差异不在技术上，在使用场景：自建存储适合单工具用户，复用 Hermes 适合两个工具并用、且已经积累了大量记忆的人。

# 插件做了什么

插件分两条独立的路径。

## 只读注入

启动时读取两个记忆文件，拼成一段文本，注册为 system prompt 的一个段：

```js
// lib/index.js
export const inject = ["systemPrompt", "tools"];

export function apply(ctx) {
  const text = buildMemoryText();      // 读 MEMORY.md 与 USER.md，拼成一段
  if (text !== undefined) {
    ctx.systemPrompt.section({
      name: "hermes:memory",
      order: SECTION_ORDER,            // 100：身份与人格之后、工具指引之前
      text
    });
  }
  // 写回工具注册，见下
}
```

三个细节值得说：

- **静态文本只注册一次**。读取发生在插件加载时，之后每次组装 prompt 复用同一份字符串，对 KV Cache 前缀稳定。想热更新可以改成每次组装时回调，代价是前缀不稳定
- **段名带命名空间** `hermes:memory`，避免和其他插件的段重名
- **顺序 100** 落在官方段落位之间：身份与人格相关段在负值到零附近，工具指引在一千以上，记忆段在中间

## 反向写回

注册一个 `memory` 工具，协议与 Hermes 内置的记忆工具对齐：

```js
// lib/memory-tool.js（工具定义摘要）
{
  name: "memory",
  description: "写入或修改 ~/.hermes/memories/ 下的长期记忆",
  schema: {
    action: "add | replace | remove",
    target: "memory | user",
    content: "条目内容",
    operations: "批量操作时使用"
  }
}
```

工具本身不直接写盘，而是 spawn 一个 python 脚本执行写入：

```js
// 写盘走 memory_store.py，stdin 传 JSON，stdout 收 JSON
const child = spawn(python, [STORE_SCRIPT], { stdio: ["pipe", "pipe", "pipe"] });
child.stdin.write(JSON.stringify(request));
```

写成功后把对应的记忆文件复制到归档仓库，执行 git add 与 commit，提交信息格式是 `memory: <target> — <说明>`。

## 两条路径互相隔离

注入和写回各自 try/catch：

- 注入失败（文件读不到、系统 prompt 服务异常）不影响工具注册
- 工具注册失败不影响注入

原因是这两件事的失败模式不同：注入失败意味着这次会话没有记忆上下文，但工具还能用；工具失败意味着不能写回，但至少能读。拆开之后，一个坏了不会连带另一个。

---

## 注入文本怎么拼

拼接逻辑很简单：

- 按固定顺序读两个文件，各自包一个小标题
- 前面加一段说明，声明这是只读上下文、不是指令
- 后面追加一段静态提示，告诉模型存在 `memory` 写回工具
- 两个文件都缺失时返回空，不注册这个段

后面那段静态提示是有意加的。只注入记忆而不告诉模型可以写，模型会把记忆当成只读材料，不会主动沉淀。提示文案里写清了工具名、target 取值与归档行为。

## 工具协议

`memory` 工具的参数与 Hermes 内置工具一致，这样模型在两个工具里的行为习惯可以复用：

| 参数 | 取值 | 说明 |
|---|---|---|
| `action` | add / replace / remove | 单条操作 |
| `target` | memory / user | 写入哪个文件 |
| `content` | 字符串 | 条目内容 |
| `operations` | 数组 | 批量操作时替代单条参数 |

`replace` 需要先用 `old_text` 定位现有条目，避免整条覆盖。批量操作走 `operations` 数组，一次提交多条修改，减少写盘与归档次数。

## 写盘流程

写盘由 python 脚本执行，Node 侧负责传参和收结果：

- Node 把操作序列化成 JSON，从 stdin 传给 python
- python 读取文件、做增删改、写回，最后从 stdout 返回 JSON 结果
- Node 收到成功后，复制文件到归档仓库并提交

用 python 而不是纯 Node 的原因是文本处理：记忆条目里中文、标点、换行混排，python 的字符串处理与文件编码行为更省心。副作用是多一个运行时依赖，安装要求本机有 python3。

## 归档设计

每次成功写入都归档一次，而不是定时提交。这样做的好处是提交历史与写入一一对应，能查到「哪次会话写了什么」。

提交信息格式是 `memory: <target> — <说明>`，说明取工具调用里传入的 note 字段，没传就写 update。翻归档历史时，语义化的说明比时间戳有用得多。

# 开发笔记

## 服务键必须是 inject 数组里的名字

Cordis 的服务访问依赖 `inject` 声明。没有声明就去访问 `ctx.systemPrompt`，会直接抛 `cannot get property without inject`，而且是运行期错误，不是启动期报错。

这和很多插件框架的「先拿后判空」不同：不声明就是硬错误，不是 undefined。

## 注入文本要消毒花括号

DSH 的 prompt 渲染对 `{{variable}}` 做严格插值，未知或畸形引用会直接抛错，导致整个 prompt 组装失败、agent 不可用。

记忆文件是用户可编辑的 markdown，里面完全可能出现 `{{` 这种字符（写代码示例时很常见）。插件在拼接时把 `{{` 拆成 `{ {` 做消毒，规避这个问题。

这个坑很难在测试里发现，因为正常情况下没人会在记忆里写模板语法。但只要出现过一次，故障现象是「agent 完全起不来」，排查成本很高。

## 为什么不用 sessionProjections

DSH 官方有一个 `agent-instructions` 插件，走的是另一条路：把内容构造成 user-role 消息塞进对话历史，用钩子跟踪文件变化。

那条路适合「会变的工作区文件」，不适合「固定的记忆文本」：

- 记忆是启动时读一次的静态内容，不需要刷新
- 塞进对话历史会占用上下文，还会破坏 KV Cache 前缀
- 静态文本用 `section()` 一次注册，依赖少、行为可预期

## 跨平台的两个坑

Windows 上踩了两处：

- `process.env.HOME` 在 Windows 未定义，改用 `os.homedir()`。低版本代码在 Windows 上会读到一个空路径，表现是记忆永远为空
- `spawn` 的同步版本在某些 Windows 环境会报 `uv trampoline failed to spawn Python child process`，改用 `spawnSync` 并显式探测可用解释器（先试 `python3`，再试 `python`）

这类问题的共同点是：在 Linux 上完全正常，换到 Windows 才暴露，而且错误信息指向的不是根因。跨平台插件的调试成本主要在这里。

## KV Cache 与静态文本

system prompt 是缓存前缀的一部分，内容变化会导致缓存失效。插件选择在加载时读一次、注册一次，之后复用同一份静态文本，换来的就是稳定的前缀。

代价是记忆不热更新：会话进行中改了记忆文件，当前会话看不到变化，要等下一次启动。这个取舍是刻意做的，记忆的更新频率远低于会话切换频率，热更新的收益不值得破坏缓存。

## 失败隔离的日志

注入与写回各自 try/catch，且日志分开写：

- 注入失败记 `hermes-memory: 注入失败，已跳过`
- 写回注册失败记 `hermes-memory: 写回工具注册失败，已跳过`

分开的理由是排查。两种失败原因完全不同：注入失败多半是文件权限或服务异常，写回失败多半是工具 schema 冲突。混在一条日志里，排查时要读代码才能区分。

## 测试

仓库里有两个测试：

- `test_tool.mjs`：工具注册与参数校验，不实际写盘
- `test_store.py`：python 侧的增删改逻辑，用临时目录

测试覆盖不到的是真实 DSH 环境里的加载行为，比如服务键拼错、插件顺序问题。这类问题只能在实际启动时验证，所以每次改注入逻辑都重启一次确认。

## 记忆条目的生命周期

一条记忆从写到删，通常经历三个阶段：

| 阶段 | 特征 | 处理 |
|---|---|---|
| 新增 | 解决一次新问题后写入 | 保留 |
| 替换 | 同一问题出现更好的结论 | 覆盖旧条目 |
| 淘汰 | 结论过时或只适用于临时状态 | 删除 |

实际维护里，第二阶段最频繁。同一条环境事实用了两三个月，往往被改写三四次，每次都是补充边界条件。删掉的条目不多，但保留的条目都经过多轮修订。

# 用起来的实际效果

一段真实的记忆条目长这样（脱敏）：

```markdown
§
DSH: 四模式,patch扁平-id,事故见dsh-deploy(P20 OOM;fix-dsh-tools勿砍);
技能=~/.agents/skills(根级软链=入口;包内新增须补软链); 重启=kill MainPID;
**why_*(thoughtdag)进程内建索引会OOM杀dsh,禁用**。
```

风格是压缩过的：能省的虚词全省，用符号和缩写。原因还是字符上限，2200 个字符要装下所有环境事实，只能这么写。

这些条目在 DSH 会话里确实起作用。举两个实际发生的例子：

- 会话里出现 OOM 崩溃，模型读到记忆里「为什么工具会建索引导致 OOM」的条目，直接建议禁用而不是从头排查
- 新增技能没有被注册，模型读到「包内新增须补软链」的条目，直接指出根因

写回的价值不是「模型记住我说的话」，而是「下次遇到同类问题时不用重新诊断」。140 次写回里，大部分是这种可复用的诊断结论。

## 触发时机

插件没有做任何自动触发：没有斜杠命令、没有轮次提醒、没有压缩前抢救。唯一的路径是模型判断后调用工具，而判断依据来自注入文本末尾那句静态提示。

但调用记录能看出实际时机的规律。按会话内轮次统计 113 次调用：

| turn | 次数 | 典型场景 |
|---:|---:|---|
| 1 | 11 | 会话开头就写：用户明确给出事实或纠正模型 |
| 2-3 | 16 | 场景刚建立完，模型顺手记下 |
| 7-16 | 17 | 任务中途补充结论 |
| 8 | 36 | 峰值：任务告一段落、发现新环境事实 |
| 42 以上 | 21 | 长会话后段，整理式写入 |

每个会话的调用次数也说明了行为：两次最常见（15 个会话），一次（6 个）、三次（5 个）、五次（4 个），最多的一个会话调了 13 次。

操作类型上，批量 `operations` 52 次，单条 `replace` 38 次，单条 `add` 23 次。批量多于单条，说明模型倾向攒几条一起提交，而不是遇到一条写一条。

这套行为不是设计出来的，是提示文案加模型判断的自然结果。没有 nudge 的情况下，写回频率完全取决于模型对「值得长期沉淀」的把握。

## 写回模式的观察

翻调用记录能看到几种典型模式：

- 一次会话里连调三到五次，通常是在整理一批环境事实，做完累加后压缩成两三条
- 隔几天调一次，多是遇到新问题后补充诊断结论
- 长时间不调用，说明这段时间在重复已知工作，没有新事实需要沉淀

第二种模式最有价值：新问题解决后立刻写回，下次遇到同类问题可以直接复现诊断路径。

## 一个反例

不是所有写回都该保留。有过几条记忆是当时的临时状态（某个服务正在迁移、某个配置临时改了），过几天就失效，但留在文件里会让模型误判当前状态。

处理办法是在新会话里主动替换或删除这类条目。记忆不是只增不减的日志，旧条目的清理和新增同样重要。

# 安装

插件是标准的 DSH 插件包，通过 profile 的依赖安装：

```json
// ~/.dsh/profiles/<profile>/package.json
{
  "dependencies": {
    "dsh-hermes-memory": "file:/path/to/dsh-hermes-memory"
  },
  "dsh": {
    "profile": {
      "bundles": ["dsh-hermes-memory"]
    }
  }
}
```

装完重启 DSH，会话开头会多出一段记忆内容。记忆文件在 `~/.hermes/memories/`，归档仓库默认 `~/Dev/hermes-memories/`，两者都可以用环境变量覆盖。

源码在 [Chieko3020/dsh-hermes-memory](https://git.chieko3020.xyz/Chieko3020/dsh-hermes-memory)，MIT 许可，带两个测试脚本。

## 验证安装

装完重启，按三步确认：

- 会话开头出现记忆内容：说明注入生效
- 问一个记忆里有的环境事实：模型能答对且不臆造，说明内容完整
- 让模型「记住这条」：观察是否调用了 `memory` 工具，以及归档仓库是否多一次提交

三步都不通过时，先看 DSH 启动日志里的 `hermes-memory` 关键字，注入与工具注册各自有独立的失败日志。

## 没有自动提醒

Hermes 有两个主动机制：每十轮提醒保存（`nudge_interval`），压缩前给一轮保存机会（`flush_min_turns`）。本插件都没有实现。

后果是具体存在的：长会话进行到后期，如果模型一直没主动写，压缩掉的内容就真的丢了；Hermes 在同样场景下至少有一次抢救。

这不是设计取舍，是尚未补上的能力。DSH 的 agent 循环有会话事件与钩子，接上这两个机制在技术上是可行的，只是优先级排在功能可用之后。

# 记忆与技能的分界

这套东西用久了会发现两个容易混的概念：记忆和技能。

| 维度 | 记忆 | 技能 |
|---|---|---|
| 存什么 | 事实与结论 | 流程与方法 |
| 什么时候用 | 每次会话自动注入 | 需要时主动加载 |
| 谁维护 | 模型按需写回 | 人写，模型执行 |
| 例子 | 某个服务重启命令、某次故障的根因 | 审查流程、写作规范 |

判定的标准可以简化成一句话：换一台机器还需要带着走的是技能，只对当前环境成立的是记忆。

混用会出问题。把流程写进记忆，条目会膨胀到字符上限，而且每次会话都占上下文；把环境事实写进技能，技能就失去通用性，换环境要重写。分开之后两边都简单：记忆保持二十多条的高密度，技能保持与具体环境无关。

# 边界

这个插件不做的事，和它做的事同样重要。

- 不做向量检索。记忆是全文注入，靠模型自己判断相关性，规模上限就是字符上限
- 不做自动写入。写不写、写什么，由模型判断后调用工具，没有后台任务
- 不做冲突检测。两条记忆内容矛盾时，靠模型在会话里自己发现
- 不与 Hermes 实时同步。两边读写同一个文件，但不做锁与合并，同时写会互相覆盖

这些边界来自一个判断：记忆的价值在「经过策展的少量高价值事实」，不在「尽可能多的历史」。向量检索和自动写入适合的是另一种需求，不是这个插件要解决的问题。

四条边界各自的原因：

- 不做向量检索：记忆条目只有二十多条，全文注入的上下文成本可以接受；上到几百条才需要检索，到那时字符上限早就逼着模型压缩了
- 不做自动写入：自动写入的内容质量不可控，写进去的错误事实比没写更糟；让模型判断再调用，等于每一次写入都过一遍「这值得长期记住吗」
- 不做冲突检测：矛盾的记忆会在使用中暴露，模型读到两条冲突条目时通常会在回答里指出；加自动检测需要额外的语义比较，复杂度不成比例
- 不做实时同步：两边同时写同一个文件的概率很低，加锁与合并的收益不足以支撑复杂度；真需要并发编辑时，用 git 归档回滚更直接
