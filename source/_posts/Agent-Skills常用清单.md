# 写在前面

用 Agent 写代码一年多，装过的 skill 有几十个，但真正常驻的没几个。之前一直凭印象说"我常用这几个"，直到想写这篇文章才决定认真统计一次：会话日志里到底记录了哪些技能调用。

统计完得到两个结果，一个是数据，一个是认知上的修正。数据列在下面的清单里；修正的部分是，我原以为最常用的是求职那一套技能，实际排在前面的全是编码工作流里的规划、执行与审查技能。主观印象和真实使用有偏差，这件事本身就值得写下来。

文中的数据来自两个操作系统、三套 harness 的本地日志：Linux 上 DSH 160 个会话、Codex 80 个会话；Windows 上 DSH 53 个会话、Codex 22 个会话。统计脚本和口径都写在文里，读者可以拿去统计自己的。

---

# 这批技能的来路

清单里的技能分两部分。

## 第三方部分

主体来自 [matt-skills-with-to-goal](https://github.com/tt-a1i/matt-skills-with-to-goal)，一个基于 [mattpocock/skills](https://github.com/mattpocock/skills) 的 fork，MIT 许可。作者把技能按 engineering 与 productivity 两类组织，核心思路是把"把任务边界写清楚"这件事拆成若干可组合的技能，而不是规定一套固定流程。

我实际在用的是其中这些：

- grill 系列：`grilling`、`grill-me`、`grill-with-docs`
- 规格与拆分：`to-spec`、`to-tickets`、`to-goal`
- 执行与审查：`spec-executor`、`code-review`
- 辅助：`diagnosing-bugs`、`research`、`handoff`、`domain-modeling`

## 自有部分

另一部分是自己写的，集中在编码工作流与求职两条线上：

- `dw-plan`、`dw-execute`、`dw-review`：三段式工作流，规划冻结 SPEC、隔离子会话执行、双轴审查
- `blog-writing-style-chieko`、`humanizer-zh-next`：中文写作约束
- `job-setup`、`job-workflow`：求职工作区的初始化与阶段调度

这两部分合起来 22 项，下面按使用频率和实际工作流分别讲。

# 我怎么知道自己常用哪些

装技能容易，知道哪个真在用不容易。我的判断曾经完全靠印象，后来发现有两个盲区。

## 盲区一：模型调用和用户调用是两条通道

DSH 里技能有两条加载路径：

- 模型主动调用：走 `skill` 工具，日志记 `tool/call`，参数里有技能名
- 用户斜杠调用：输入 `/grill-me` 这类命令时，技能内容以 `<skill_content name="...">` 注入用户消息，日志里没有独立的命令事件

只看 `tool/call` 会漏掉所有斜杠调用。我最初统计只有 34 次调用，修正后斜杠部分补出 66 次。

## 盲区二：不同 harness 的记录方式不同

Codex 桌面版没有原生 skill 机制，它靠执行 `cat ~/.agents/skills/<name>/SKILL.md` 读技能文件。所以 Codex 的统计口径是"SKILL.md 被读取的次数"，和 DSH 的"技能加载次数"不是一回事，直接相加会偏向重复读取。

## 统计口径

按抓取方式分三类，覆盖两个主机的六个来源：

| 源 | 抓取对象 |
|---|---|
| DSH 模型调用 | `tool/call` 中 `name=skill` 的 `arguments.name` |
| DSH 用户调用 | `user/message` 中 `<skill_content name="x">` 的注入 |
| Codex | 会话日志中 `.agents/skills/<name>/SKILL.md` 的出现（Windows 侧为反斜杠路径） |

六个来源里只有四个能按技能名统计：

| 主机 | harness | 会话数 | 能否按技能名统计 |
|---|---|---:|---|
| Linux | DSH | 160 | 能 |
| Linux | Codex | 80 | 能 |
| Windows | DSH | 53 | 能 |
| Windows | Codex | 22 | 能 |
| Linux | Hermes | 1020 次加载 | 不能 |
| Windows | Hermes | 无会话数据 | 不能 |

Hermes 的 `skill_view` 日志只记录「加载完成」与字符数，不记技能名，1020 次加载只能给出总量；Windows 侧的 `.hermes` 目录只有 memories，没有会话记录。所以 Hermes 两个源不参与排序。

然后用**按会话去重**做排序，也就是"有多少个任务用过它"。原始次数会被同一会话的重复读取放大，去重后的会话数更接近"这个东西帮我处理了多少件事"。

DSH 侧的解析脚本大致长这样，日志本身是 zstd 压缩的 JSONL：

```python
import glob, subprocess, json, re, collections

files = glob.glob('/home/ubuntu/.dsh/sessions/*/*/session.v4.jsonl.zstd')
pattern = re.compile(r'<skill_content name="([^"]+)"')
per_session = collections.defaultdict(set)

for f in files:
    raw = subprocess.run(['zstd', '-dc', f], capture_output=True).stdout.decode('utf-8', 'ignore')
    sid = f.split('/')[-2]
    for line in raw.splitlines():
        # 斜杠调用：技能内容注入在用户消息里
        if 'skill_content' in line:
            data = json.loads(line).get('data') or {}
            for block in data.get('content', []):
                for name in pattern.findall(block.get('text', '')):
                    per_session[sid].add(name)
        # 模型调用：skill 工具的 arguments 里有技能名
        elif '"skill"' in line:
            call = json.loads(line)
            if call.get('type') != 'tool/call':
                continue
            data = call.get('data') or {}
            if data.get('name') == 'skill':
                args = json.loads(data.get('arguments') or '{}')
                per_session[sid].add(args.get('name'))
```

去重时用 `per_session[sid]` 这个集合，同一会话内同一技能只算一次。

## 三个已知偏差

- DSH 统计包含子 agent 会话，一个任务派十个子代理会放大计数
- Codex 的读取次数包含同一会话的反复读取，所以只能用于排序
- Windows 侧的日志通过 SSH 取回本机解析，两个主机的会话不重叠
- 本文写作过程中我自己加载了 `grilling`，它的会话数要减 1

# 一条需求的生命周期

清单是横向的，实际使用时技能是纵向串起来的。一个从模糊需求到代码合入的完整过程大致这样走：

```
需求澄清        grilling / grill-me
  冻结规格      to-spec
    规划确认    dw-plan
      实现      dw-execute / spec-executor
        审查    dw-review / code-review
  出问题时诊断  diagnosing-bugs
  需要外部事实  research
  换会话交接    handoff / chieko-handoff
```

这条链路不是强制的流水线。小的改动直接从实现开始，只有需要跨会话、跨人的任务才走完整链路。技能的价值在于每一段都有明确的输入输出边界，不会出现"讨论到一半开始写代码"或者"写完了发现需求理解错了"。

下面按这条链路的顺序逐个讲。

---

# 需求澄清：grill 系列

三个技能解决的是同一件事的不同层次。

## grilling

质询引擎。输入是一个计划、决策或想法，输出是一份经不起追问的地方被追问过的共识。

它的工作方式是按设计树展开：每个决策都会分叉出依赖它的决策，技能按"前置条件已确定"的边界分轮提问，每轮把所有能问的问题一次问完，每个问题附上推荐答案。这样不会出现问到一半发现前面的答案推翻后面问题的情况。

典型用法是直接说"grill 我这个方案"，然后跟着它的编号回答。

不该用它的时候也要说清楚：问题本身很小、三句话能说清楚时，质询会变成绕圈子。判断标准是每次追问是否产生了新的决策分支，连续两轮没有新分支就该停。

## grill-me

`grilling` 的入口别名，一句话触发。日常用得多的是它，因为不需要解释要做什么，`/grill-me` 之后跟一句话就够了。

## grill-with-docs

质询的同时维护领域词汇表和 ADR 文档。适合需求会沉淀成文档的项目：一边问清楚，一边把术语和决策落盘。

三者的取舍：**引擎与入口分开**，是因为入口可以换（不同 harness 的斜杠命令支持不同），引擎只有一份，改逻辑只改一处。`grill-with-docs` 是带副作用的版本，只在需要产出文档时用。

---

# 领域词汇：domain-modeling

维护领域词汇表与架构决策记录。它处理的是一个具体问题：同一个概念在不同人的说法里叫法不同，写到代码里就变成三四个名字。

用在项目刚开始、或者发现同一个概念出现多种叫法的时候。产物是术语表和 ADR：术语表定下实体、动作、边界怎么叫，ADR 记下已经做过的取舍，不留在会话里。

`grill-with-docs` 在质询时会调用它，把讨论中确认的术语直接落进文档。单独使用时也能做一件事：扫一遍现有代码和文档，把叫法不一致的地方列出来。

# 冻结规格：to-spec 与拆分

## to-spec

把已经达成共识的讨论整理成一份可执行的 SPEC，发布到项目的 issue tracker 或本地文件，末尾带 `SPEC READY` 标记。

冻结这个动作的意义在于：讨论阶段可以有分歧，冻结之后实现阶段不再重新讨论。避免实现到一半又回到需求层面扯皮。

## to-tickets

把 SPEC 拆成带依赖关系的工作切片，每张工单足够小，能让一个 agent 在一个会话里完成，并且能独立验证。

## to-goal

把已批准的来源编译成可搬运的执行合同，包含当前状态、执行顺序、完成标准、约束和上下文。它的价值在跨会话、跨人、跨引擎的场景，换一个执行者之后仍然按同一份标准交付。

## 三项合计 0 次的说明

这三个技能都统计为 0 次，原因不同：

- `to-tickets` 和 `to-goal` 是被 `to-spec` 的路由标记间接引用，我很少单独调用
- `handoff` 与自有的 `chieko-handoff` 功能重叠，实际用的是后者

链路完整性和实际使用频率不是一回事。写文章时保留它们，是为了说明这条链路上还有哪些位置可以放技能，不代表必须用。

# 规划确认：dw-plan

`dw-plan` 是自有工作流的第一段。

它做的事情和 `to-spec` 有重叠，区别在于它强制先问"有没有参考文档"：

- 有参考文档时调用 `grill-with-docs`，基于文档质询
- 没有时调用 `grill-me` 从零质询
- 质询完成后调用 `to-spec` 产出 `SPEC.md`，末尾必须有 `SPEC READY` 块

这个"先问参考文档"的强制步骤来自一次踩坑。项目里已经有需求设计文档和技术选型文档，但规划时如果直接从零质询，产出的 SPEC 会和既有文档脱节，实现阶段就会出现两套说法。技能里加这一步之后，规划会先读既有文档再提问。

## 设计取舍

`dw-plan` 没有自己实现质询逻辑，而是把 `grilling` 当引擎调用。这样质询能力升级时工作流自动受益，不用同步改两份。代价是它依赖第三方技能，装技能时要一起装。

---

# 实现：dw-execute 与 spec-executor

## dw-execute

接在 `dw-plan` 之后，把 `SPEC.md` 交给一个子会话执行。子会话的指令里要求严格按 SPEC 实现，运行 `spec-executor`，完成后返回 EXECUTION RECEIPT。

它解决的是上下文污染问题。规划和实现放在同一个会话里，上下文会越滚越长，到后期模型的注意力被历史决策拖住，实现质量下降。拆成两个会话之后，实现会话只拿到 SPEC，上下文干净。

## spec-executor

执行已批准的 SPEC，实现、测试、审查，最终输出带证据的 receipt。receipt 不是"我做完了"这种自报，而是逐条列出完成标准对应的证据：改了哪些文件、跑了什么命令、输出是什么。

拆会话也有成本：子会话拿不到主会话的探索过程，SPEC 写得不够具体时，实现会偏离原意。改动小、上下文短的任务直接做更划算。

## 设计取舍

`dw-execute` 负责编排（开子会话、传 SPEC、收 receipt），`spec-executor` 负责执行。两者分开是因为编排逻辑与执行逻辑的变化频率不同：编排可能换成别的 harness 的会话机制，执行逻辑基本不变。

还有一个实际原因：`spec-executor` 可以用在别的地方，不绑死在自己的工作流里。

# 审查：dw-review 与 code-review

## code-review

双轴审查，两个方向并行跑子代理：

- Standards 轴：代码是否符合仓库的编码规范
- Spec 轴：代码是否实现了原始 issue 或 spec 要求的内容

输出是两个视角并列的报告。分开两轴的意义在于，规范问题和需求偏差是两类不同的错误，混在一份报告里容易被"格式没问题"掩盖"功能做偏了"。

## dw-review

自有工作流的审查阶段，在 `dw-execute` 返回 receipt 之后调用。它主要确认 receipt 里的证据是否成立，以及变更是否偏离 SPEC。需要更细的审查时再调 `code-review` 做双轴扫。

## 两个技能为什么都留着

`dw-review` 是阶段性的把关，只看"有没有按 SPEC 做对"；`code-review` 是全量的代码质量审查，看"代码本身写得好不好"。前者快，后者细，场景不同。

审查强度应该跟着风险走。改一行配置跑双轴审查是浪费；改动涉及并发、内存或协议时，两轴都要跑，而且 Spec 轴要回到原始需求逐条对。

# 排障与调研

## diagnosing-bugs

疑难 bug 的诊断循环。它的流程是复现、缩小范围、二分定位、提出假设、验证假设，每一步都要求留下证据，而不是靠猜。

适合的场景是"问题偶发、复现不稳定、或者报错信息指向的位置和根因相隔很远"。普通 bug 直接看堆栈就够了，用不上这个技能。

## research

针对一个问题去高可信度的一手来源查证，把结论落成仓库里的 markdown 文件。

它的约束是不能拿二手博客当结论，也不能凭记忆写。要求落到一手来源这件事，对技术选型和接口行为这类容易过时的信息特别重要。

---

# 交接：handoff 与 chieko-handoff

## chieko-handoff

把当前会话压缩成结构化交接文档，让另一个 agent 接手。文档结构固定：当前状态、已完成、卡在哪、下一步、验证方式。

关键设计是交接文档放在公共位置而不是工作区，不同 harness 的 agent 都能读到。文档里带 `from` 字段标明来源，接手方知道上一段是哪个工具做的。

## handoff

同类技能，统计为 0 次，实际没在用。保留在清单里是因为它和 `chieko-handoff` 是同一类能力的两个实现，读者可以按自己习惯选。

## 设计取舍

交接文档最容易写错的地方是写成会话流水账。有效的交接要按状态组织，不按时间组织：已经做出什么、现在在哪、下一步做什么。技能里把这一点写成了硬性要求。

# 写作：blog-writing-style-chieko 与 humanizer-zh-next

## blog-writing-style-chieko

博客的写作约束。它把风格拆成可检查的规则：

- 严肃中性，不用删除线、meme、括号吐槽、emoji、口语化连接词
- 以 bullet points 和表格组织内容，少用长段落
- 技术文章开头交代写作动机
- 正文不用 Unicode 箭头，方向用文字描述
- 不写前向或后向的章节引用，每节自包含
- 引用的源码和数字必须可核查

这个技能的有趣之处在于它是一份**负面清单**：大部分篇幅在讲不要什么。写作风格这种东西，正面描述"要严谨"没有可操作性，列出"不要 emoji、不要括号吐槽、不要去提上面讲过什么"才能直接约束输出。

## humanizer-zh-next

中文文本去 AI 腔。检测并修复几类模式：夸大的象征意义、宣传性语言、破折号过度使用、三段式法则、否定式排比。

用法是写完初稿后过一遍，标出 AI 痕迹再改写。它和风格技能是互补关系：风格技能在写之前约束，去 AI 腔在写之后检查。

# 求职链路：job-setup 与 job-workflow

这条链路是最近重构过的，从原来的七个技能合并成"一个初始化入口加一个阶段调度"。

## job-setup

阶段 0，初始化求职工作区。它解决的是"新装技能之后工作区是空的，不知道从哪开始"的问题。

流程分四步：

- 环境检查：建立目录骨架
- 偏好配置：把求职方向、题库范围、简历偏好写进配置文件
- 素材导入：给一张对照表，告诉用户旧简历、项目代码、培养记录、工作汇报这些材料该放哪
- 生成档案：按依赖顺序触发阶段技能，最终输出体检报告

第三步是重点。多数人不知道自己手里的材料该怎么归类，给它一张"你有的东西放这个目录"的映射表，比让它自己去猜有效得多。

## job-workflow

阶段调度。启动时先检查工作区是否初始化，未初始化就提示先跑 `job-setup`；已初始化则检查五个阶段的完成状态，输出状态面板，引导跳转。

它本身不产出任何内容，只负责判断"现在该做哪个阶段"。这个设计来自一次重构：原来的调度技能里混了大量规范，和阶段技能的内容重复，改一处要同步改三处。拆开之后调度只做调度。

# 三条设计取舍

清单讲完，回头说几个贯穿所有自建技能的原则。

## 规则、配置、数据三层分离

技能目录只放规则：流程、协议、模板、默认值。个人配置放在工作区的配置文件里，原始素材和生成产物放在工作区目录里。

这样做的好处是一次性的：技能可以整目录公开、随时升级，不会因为里面混了个人数据而需要脱敏；配置改一处就能改变行为，不用改技能文本；升级技能不会覆盖个人设置。

判断标准可以简化成一句话：换一个人用，这句话还需要改吗。需要改的进配置或数据，不需要改的留在技能里。

## 技能粒度

一个技能只做一件事，用斜杠命令串联。不做大而全的"一站式"技能。

原因是技能内容会进入上下文，大技能每次加载几百行，真正用到的可能只有其中一段。拆小之后按需加载，上下文成本低很多。代价是技能之间的依赖要显式声明，装的时候要装全。

## 第三方依赖

第三方技能用 vendor 的方式随仓库分发，保留原始许可文件。好处是装完即用，不依赖外部仓库可用性；代价是升级要手动同步。

这里有一个容易踩的坑：第三方技能之间有传递依赖。`grill-me` 的内容第一句是"跑一个 grilling 会话"，如果只装 `grill-me` 没装 `grilling`，这个技能就是个空壳。所以 vendor 的时候要按引用关系把传递依赖补全，不能只看直接引用。

# 为什么不写死流程

有人问过为什么不把这些技能串成一个固定的流水线，一次调用跑完全程。试过，效果不好。

固定流程的问题在于它假设所有任务同构。实际任务差异很大：改一个 typo 不需要质询和 SPEC，重构一个模块可能只需要质询不需要拆分，跨周的大任务才需要完整链路。流水线把简单任务也拖进重流程，成本高到没人愿意用。

现在的做法是每个技能独立可用，用斜杠命令按需串联。链路清晰但不强制，使用者自己判断这次需要走到哪一步。代价是对使用者的判断力有要求，好处是不会为了流程而流程。

# 装在哪里、怎么共存

技能文件都在 `~/.agents/skills/` 下，DSH、Codex、Claude Code 读同一个位置。目录组织有两个层次：

- 包目录：一个包可以包含多个技能，便于统一管理
- 入口软链：根目录下每个技能一个软链，指向包内的具体目录

这个结构有一个容易忽略的约束：**新增技能之后必须补入口软链**，否则技能文件在磁盘上存在，但不会被注册。我给技能包加了一个新技能，重启服务后仍然调不到，排查半天才发现是缺了根目录的软链。第三方技能展开时也是同样的问题，扁平展开到根目录才能被发现。

与 harness 相关的一个差异：DSH 有原生的技能加载机制，`skill` 工具和斜杠命令都能触发；Codex 桌面版没有，它靠读取 SKILL.md 文件来使用技能。同一个技能文件在两个工具里都能用，但调用方式和统计口径不同。

# 怎么开始

如果只想试一两个，建议这个组合：

- `grilling`：用在任何"方案还没想清楚"的场合，成本最低，收益最直接
- `code-review`：用在准备合入的变更上，双轴审查能抓出需求偏差

这两个技能都不依赖其他技能，装上就能用。

统计自己的使用频率也很简单：日志都在本地，上面那段脚本改一下路径就能跑。跑完可能会发现，你以为常用的和实际常用的不是同一批。
