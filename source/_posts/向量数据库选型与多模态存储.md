- 某次面试被连续问到三个问题：说一下常见的向量数据库、各自的优缺点、区别和使用场景；向量数据库和传统数据库有什么区别；既然向量库存的是 bi-encoder 产生的向量，那能不能存图片、音频等其它类型的数据。
- 当时只答出了“向量库存语义向量，传统库存结构化数据”，具体方案说了一两个；图片和音频则答成“先转成二进制再存”。这个回答把“二进制序列化”和“embedding”混在了一起，面试官继续追问时就没有内容了。
- 这里按“概念、方案、选型、多模态”重写一份，作为复习记录。

# 太长不看

- 向量数据库不是“能存向量的数据库”这么简单，核心是 ANN 索引、元数据与过滤、持久化、并发和运维的一整套组合。
- 常见方案大致分四类，边界有重叠：向量索引库（FAISS）、专用向量数据库（Milvus、Qdrant、Weaviate、Pinecone、Chroma）、传统数据库的向量扩展（pgvector、Elasticsearch、Redis）、托管服务。
- 选型看数据量、过滤条件、混合检索、一致性、运维成本和团队熟悉度，不能只看厂商 benchmark 排名。
- 图片和音频存的是 embedding 与元数据，原始文件放对象存储；二进制字段可以存，但不等于能按内容检索。
- bi-encoder 是生成向量的模型，不是数据库里的数据类型；CLIP、ResNet、Whisper 也能产生向量。

# 向量数据库解决什么问题

- 传统数据库的 B+ 树、哈希、倒排索引擅长精确匹配：`id = 42`、`status = 'paid'`、`title LIKE '%foo%'`。它们不擅长“找语义上最相近的 k 条”。
- 向量检索把文本、图片、音频转成高维向量，用距离度量衡量相似度，再取 top-k。常见距离是 cosine、内积和 L2。
- 完整链路是：原始数据经过 embedding 模型得到向量，写入向量索引；查询时把 query 也转成向量，在索引里找近邻，再按元数据过滤、按业务规则重排，再返回 payload。
- 距离度量要和 embedding 模型匹配。模型输出已归一化时，余弦和内积等价；未归一化时用 L2 或先归一化。训练、索引和查询要用同一种度量，不能混。
- ANN 索引是向量检索的核心。Flat 是全量精确扫描；IVF 先聚类再扫部分倒排桶；PQ 把向量分段量化压缩；HNSW 用分层图做贪心搜索。它们的取舍集中在内存、召回和延迟。

| 索引 | 基本思路 | 内存 | 召回 | 适用 |
| --- | --- | --- | --- | --- |
| Flat | 全量暴力比较 | 100% | 精确 | 小数据、召回基准 |
| IVF | k-means 聚类，查询扫 nprobe 个桶 | 较高 | 取决于 nprobe | 分布稳定、批量查询 |
| PQ | 分段量化成码本 | 低 | 有损，常配重排 | 内存受限的大规模数据 |
| HNSW | 多层图，逐层贪心搜索 | 较高 | 高 | 低延迟、高召回 |

- 但向量数据库不只提供一个索引。它还要负责元数据与 payload、过滤、增删改、持久化、副本、备份、多租户、权限和监控。FAISS 只是一个索引库，把这些东西留给应用自己搭。
- 这也是面试里最容易漏掉的一层：把“向量检索算法”和“向量数据库”当成同一个东西。

# 和传统数据库的区别

| 维度 | 传统数据库 | 向量数据库 |
| --- | --- | --- |
| 数据模型 | 行、文档、键值，字段有明确类型 | 向量加 payload，payload 里放 id、标签、权限、URI 等 |
| 查询方式 | 精确条件、范围、JOIN、聚合 | top-k 近似近邻，再加元数据过滤 |
| 索引结构 | B+ 树、LSM、倒排、哈希 | HNSW、IVF、PQ、DiskANN 等 |
| 事务与一致性 | ACID、事务、强一致 | 多数是最终一致，事务能力有限 |
| 更新与删除 | 原地更新、事务回滚 | 常见 tombstone、compaction、重建索引 |
| 扩展方式 | 主从、分片、读写分离 | 分区、副本、存储计算分离 |
| 典型场景 | 交易、账务、报表、结构化查询 | 语义检索、RAG、推荐、去重、多模态检索 |

- 向量数据库不是传统数据库的替代品，而是另一条访问路径。需要事务、JOIN、强一致时，传统数据库仍然更合适；需要大规模语义近邻时，向量索引更合适。
- 边界正在变模糊。pgvector 让 Postgres 直接拥有向量列和 HNSW/IVFFlat 索引；Elasticsearch 的 `dense_vector` 把向量检索和 BM25 放在同一个引擎；Redis 也提供向量搜索。反过来，专用向量数据库也在补 payload 过滤、混合检索和多租户。
- “向量数据库存的是 bi-encoder”这个说法不准确。数据库存的是 embedding 向量，bi-encoder 只是产生向量的一种模型架构。换一个 embedding 模型，向量维度、距离分布和检索效果都会变，所以模型版本要跟数据一起记录。

# 常见方案对比

| 方案 | 形态 | 索引与过滤 | 优点 | 局限 | 适用 |
| --- | --- | --- | --- | --- | --- |
| FAISS | C++/Python 库 | Flat、IVF、PQ、HNSW，GPU 支持 | 快、灵活、离线可用 | 不是数据库，服务化、事务、元数据过滤、权限都要自己搭 | 研究、离线批处理、嵌入式检索 |
| Milvus | 分布式服务，也有 standalone | HNSW、IVF、PQ、DiskANN 等，标量过滤、混合检索、多租户 | 功能全、规模大、存储计算分离 | 组件多，运维重 | 亿级向量、独立向量服务 |
| Qdrant | Rust 服务 | HNSW、payload 过滤、量化、稀疏向量、分布式 | 轻量、过滤强、部署简单 | 超大规模要自己做容量规划 | 中小到大规模、强过滤 RAG |
| Weaviate | Go 服务 | HNSW 加倒排索引、hybrid、模块、多租户、blob | 内置 vectorizer 和生成模块，混合检索方便 | schema 和模块有学习成本，资源开销不低 | RAG、多模态、想少写胶水 |
| Pinecone | 托管 serverless | 专有索引，metadata filter、namespace | 零运维、弹性 | 闭源、不能自托管、成本和锁定 | 不想运维的团队 |
| Chroma | 嵌入式或 Cloud | dense、sparse、hybrid、metadata filter | 上手快、开发体验好 | 大规模和 HA 要按部署形态评估 | 原型、本地、中小规模 |
| pgvector | Postgres 扩展 | HNSW、IVFFlat，SQL 过滤、JOIN、ACID | 一套库、事务一致、运维熟悉 | 索引构建吃内存，vacuum 和大规模分片要另做 | 已有 Postgres、百万级、强一致 |
| Elasticsearch | 搜索引擎 | dense_vector、HNSW、BM25 hybrid、聚合 | 混合检索成熟，工具链完整 | JVM、内存和运维成本高 | 已有 ES、日志加语义搜索 |
| Redis | 内存数据库 | HNSW、FLAT | 低延迟、现成缓存 | 内存成本高，容量和持久化要权衡 | 会话、缓存、中小规模低延迟 |

- 这张表只能给方向，具体版本的能力边界要查对应文档。向量数据库的迭代很快，索引类型、量化方式和过滤策略经常变。
- 托管服务不是另一类数据库，而是把 Milvus、Chroma 或自研引擎包成云服务。选托管还是自托管，本质是运维能力和成本的分工。

# 选型维度

- 数据量与维度：先算原始向量占多少内存。维度 768、1000 万条、float32，仅向量就是约 30GB，HNSW 还要加上图结构。量化、半精度和磁盘索引会改变量级。
- QPS 与延迟：看 p95 和 p99，不只看平均。HNSW 的 `ef_search`、IVF 的 `nprobe`、PQ 的重排都会影响延迟和召回。
- 过滤条件：这是最容易翻车的地方。按租户、时间、类目过滤时，后过滤可能凑不满 k 条，预过滤可能扫描过多，图内过滤又要看引擎实现。
- 混合检索：是否需要 BM25 加向量、RRF 融合、cross-encoder 重排。已有 Elasticsearch 或 Weaviate 时，混合检索的胶水会少很多。
- 一致性与事务：向量库是否要和业务库在同一个事务里更新。pgvector 在这点上最自然；独立向量库通常要做补偿和对账。
- 更新与删除：HNSW 的删除不是真正摘除节点，常见做法是 tombstone 加 compaction。更新频繁时，要评估重建成本和查询抖动。
- 多租户：共享一个大索引可能让不同租户的向量互相影响召回。namespace、partition、独立 collection 各有成本。
- 运维与成本：自托管要人、要监控、要备份；托管要钱、要接受厂商锁定。内存、副本、跨区流量都要算进去。
- 合规与数据驻留：数据能不能出域、能不能加密、审计日志够不够，往往比 benchmark 更能决定选型。
- 团队熟悉度：已有 Postgres 的团队上 pgvector，通常比新引入一套分布式向量库更快落地。

# 场景映射

- 已有 Postgres，数据在百万级，需要事务、JOIN 和强一致：优先 pgvector。先把 HNSW 参数和 `maintenance_work_mem` 调好，再评估要不要独立向量库。
- 亿级向量，独立 RAG 服务，多租户，要求水平扩展：Milvus 或 Zilliz Cloud。接受组件多和运维成本。
- 中小规模，过滤条件复杂，想轻量自托管：Qdrant。单机部署简单，payload 过滤和量化够用。
- 已有 Elasticsearch，既要 BM25 又要语义检索：Elasticsearch 的 `dense_vector` 加 hybrid 查询，避免多一套系统。
- 不想运维，接受按量计费和厂商锁定：Pinecone、Chroma Cloud、Zilliz Cloud 这类托管服务。
- 离线批处理、研究、嵌入式检索：FAISS。把它当成索引库，不要指望它提供数据库能力。
- 低延迟缓存、会话、中小规模：Redis 向量搜索。内存成本要先算清楚。
- 原型和本地开发：Chroma 或其他嵌入式方案，先把链路跑通，再决定是否迁移。

# 图片和音频怎么存

- 向量数据库存的是 embedding，不是像素和采样点。图片经过 CLIP、ResNet 等模型得到向量，音频经过 Whisper、CLAP 等模型得到向量，数据库只负责索引这些向量和它们的元数据。
- 原始图片和音频通常放对象存储，例如 S3、OSS、MinIO。向量库的 payload 里存 URI、类型、标签、权限、时间、模型版本，查询命中后按 URI 去对象存储取原文件。
- “转成二进制再存”错在把序列化当成了语义表示。二进制字节当然可以存进 blob 字段，但 ANN 索引比较的是向量；没有 embedding，存了也不能按内容检索。
- 有些数据库确实支持二进制字段：Weaviate 的 `blob` 接收 base64 编码的二进制，pgvector 所在的 Postgres 可以用 `bytea`，Elasticsearch 也有 binary 字段。能存不代表应该存。大文件会把备份、复制、内存和访问路径都变重，通常还是对象存储更合适。
- binary vector 是另一回事。它把 embedding 量化或哈希成 bit，用 Hamming 距离做比较，目的是压缩和加速，不是把 JPEG 字节直接塞进向量列。pgvector 的 `bit` 类型、Milvus 的二进制向量都属于这一类。
- 多模态检索的常见做法是共享向量空间。CLIP 把图片和文本映射到同一空间，文本 query 可以召回图片；图片 query 也可以召回相似图片。Qdrant 的 named vectors、Milvus 的多向量字段，可以给同一个对象存图片向量和文本向量。
- 音频通常还会存一份 transcript 和语言、时长等元数据。检索可以走向量，也可以走文本关键词，两者结合更稳。
- 一条典型的 payload 可以长这样：

```json
{
  "id": "img_123",
  "vector": [0.12, -0.03, 0.08],
  "payload": {
    "uri": "s3://bucket/images/img_123.jpg",
    "type": "image",
    "tags": ["cat", "outdoor"],
    "model": "clip-vit-b32",
    "created_at": "2026-11-01"
  }
}
```

- `model` 和维度要记录。换 embedding 模型后，旧向量和新向量不在同一个空间，必须重新生成或双写过渡，不能直接混在一个索引里比较。

# 常见坑

- 过滤加 ANN 的后过滤会少返回。先取 top-k 再按条件筛，条件一严就不足 k 条；预过滤又可能把候选集扩得太大。要确认引擎是预过滤、后过滤还是图内过滤，并用高基数条件压测。
- HNSW 的内存常被低估。图结构、原始向量、副本和量化前的重排数据都要算；只按“向量条数乘维度”估算会偏小。
- 删除和更新不是免费的。tombstone 会占空间，compaction 会带来 IO 和延迟抖动；更新频繁的场景要提前设计重建窗口。
- 量化会损失召回。PQ、int8、binary quantization 都需要重排或过采样补救；不要只看内存下降。
- 多租户共享索引会互相影响。租户 A 的向量多了，租户 B 的召回和延迟都可能变差；namespace 或独立 collection 不是没有代价。
- 厂商 benchmark 不能直接套。数据集、维度、过滤比例、硬件和召回目标不同，结果没有可比性；用自己的 query 集和业务过滤条件压测。
- 精确匹配和结构化查询不要硬上向量库。该用 B+ 树、倒排或 SQL 的场景，向量检索只会更慢、更贵。
- 模型版本漂移要管。embedding 模型升级、维度变化、归一化方式变化，都会让旧索引失效；要有重建和双写方案。

# 面试口径

- 30 秒版：向量数据库是 ANN 索引加 payload、过滤、持久化和运维的一整套系统；常见方案分索引库、专用向量库、传统库扩展和托管服务；选型看数据量、过滤、混合检索、一致性和运维；图片音频存 embedding 和 URI，原始文件放对象存储。
- 2 分钟版：先讲向量库和传统库的区别，再分四类方案各举一两个代表，再落到场景。FAISS 是库不是数据库；Milvus 适合大规模独立服务；Qdrant 轻量、过滤强；pgvector 适合已有 Postgres；Pinecone 是托管；Chroma 适合原型。
- 被追问“能不能存图片”时，先纠正概念：存的是图片的 embedding，原始图片在对象存储；blob 可以存，但检索仍靠向量；binary vector 是压缩后的向量，不是图片字节。
- 被追问“为什么不用传统数据库”时，回答访问路径不同：精确查询用 B+ 树，语义近邻用 ANN；两者可以共存，pgvector 和 Elasticsearch 就是共存的例子。
