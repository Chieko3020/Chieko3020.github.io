# 项目背景

## 业务

云手机是把 Android 系统跑在服务器容器里的产品。用户通过浏览器看到画面、听到声音，也能把本地麦克风的声音送进云手机，让云手机里的应用以为自己在用真实麦克风。

音频方向要解决两件事：

- 远端的声音（浏览器侧）要能进到云手机，并且被应用当成麦克风输入。
- 云手机里的应用调用标准录音 API 时，不需要改代码就能拿到远端声音。

## 代理侧

代理侧是运行在云手机环境里的一个 Java 进程，负责与浏览器侧的实时通信、音频帧的接收与整理。它做这些事：

- 通过实时通信的数据通道接收音频帧。
- 解析自定义的二进制协议，拿到 PCM 数据与时间戳。
- 做乱序重排、丢包补偿、时钟对齐、增益控制。
- 通过本地套接字把 PCM 写进 Android 系统。

代理侧是数据进入 Android 之前的最后一道处理，缓冲、补偿、增益都在这里做，系统侧只负责接收与上行。

## ROM 侧

ROM 侧是 AOSP 的定制，负责把“代理侧写进来的 PCM”变成“系统里的一个麦克风”：

- 在音频框架里注册一个输入设备与模块。
- 在 audioserver 内实现一个进程内 HAL，提供输入流的读写。
- 在音频策略里声明设备、配置采样率、设置路由优先级。
- 用环形缓冲接收代理侧的数据，按录音线程的节奏提供 PCM。
- 按上层请求的采样率做重采样。

ROM 侧的改动集中在音频子系统，不涉及应用层 API 的变化，所以第三方应用可以无感使用。

## 数据流

```mermaid
flowchart LR
    B[浏览器采集] -->|实时通信数据通道| A[代理侧<br/>解析/重排/补偿/增益]
    A -->|本地套接字| S[audioserver<br/>接收服务]
    S --> R[环形缓冲]
    R --> T[录音线程]
    T -->|重采样| AR[AudioRecord]
    AR --> APP[第三方应用]
```


## 共享内核环境

云手机的部署方式是多台 Android 容器跑在同一台宿主机上，共享同一个 Linux 内核。这意味着：

- 内核里的全局资源是共享的，Binder 驱动实例、物理页池、部分锁都只有一份。
- 一个容器的异常行为可能影响其他容器，隔离性不如真机。
- 排查问题时，既要看容器内的日志，也要看宿主机内核的日志。

这个环境背景解释了两件事：为什么音频链路要自己做缓冲与背压，为什么一次内核层面的异常会让所有容器一起出问题。

# 讲一下你的实习项目

## 问题

“介绍一下你的实习，主要做了什么。”

## 我的回答

我按时间顺序讲：先做了代理端的接收与转发，再做了 ROM 侧的虚拟麦克风，最后做了音频优化，包括抖动缓冲、时钟对齐、音画同步。信息全，但没有重点，面试官追问时才逐步展开。

## 参考答案

按四段讲：

- 业务：云手机把浏览器侧的音频注入 Android，让应用用标准录音 API 拿到远端声音。
- 角色：代理侧用 Java 做接收、重排、补偿、增益；ROM 侧用 C++ 做进程内 HAL、路由、缓冲与重采样。
- 结果：第三方应用可以正常录音；代理侧与 audioserver 的资源占用都在可控范围；解决了弱网断续、时钟漂移、应用录制音视频的时长异常等问题。
- 难点：跨层时间戳一致性，浏览器时间轴、代理侧重锚、HAL 时间戳、录音线程采样率、容器时长五处联动。

## 相关知识点

### 为什么按四段讲

面试官听项目介绍，想快速知道三件事：你做什么、做成了什么、难在哪。时间顺序适合写周报，不适合面试。四段结构把“业务、角色、结果、难点”一次给全，面试官可以顺着任何一段追问。

### 结果怎么量化

结果不要只说“完成了”，要给可验证的数字或现象：

- 第三方应用能用标准 API 录音，系统相机录像正常。
- 代理侧与 audioserver 的 CPU、内存占用在联调期间有记录。
- 弱网下的断续、时钟漂移、时长异常有具体的复现与修复记录。

数字要能解释口径，比如“CPU 峰值”是在什么场景、什么分辨率、什么网络下测的。说不清口径的数字，不如不给。

### 难点怎么选

难点要选“跨层、有取舍、能讲清”的。音频链路里，跨层时间戳一致性比“写了一个 HAL”更能体现系统理解：它牵扯浏览器、代理、HAL、录音线程、容器五处，任何一处不一致都会在最终产物上放大。

# 共享内核出过什么问题，你怎么排查

## 问题

“你们的容器共享内核，出过什么问题吗？你怎么排查的？”

## 我的回答

我说共享内核确实出过一次问题：某天所有容器都无法正常开机，我主动看了 logcat、dmesg 和 tombstone。回答太短，没有讲共享内核的风险、排查顺序和结论边界。

## 参考答案

那次的现象是：多个原本正常的容器同时无法开机，不是单个应用的问题。排查时按“先确认范围、再看内核、再看容器内”的顺序：

- 先确认影响范围：是所有容器、同一台宿主机上的容器，还是某个镜像的容器。范围决定问题在宿主机、内核还是镜像。
- 看宿主机内核日志：`dmesg` 里找 panic、oops、watchdog、OOM、驱动报错。
- 看容器内日志：`logcat` 的 crash buffer、`tombstone` 的 native 崩溃栈、`last_kmsg` 或 `pstore` 里的上次崩溃日志。
- 看 Binder 与资源：共享内核下 Binder 是全局资源，`dumpsys binder_calls_stats`、binderfs/debugfs 能看线程与缓冲区状态。
- 看系统状态：`/proc/interrupts`、`/proc/meminfo`、`getprop`、`perfetto` 采样。

最后做了修复，容器恢复，但根因没有完全定位。这一点要如实说：修复了不等于找到了根因。

## 相关知识点

### 共享内核的风险从哪来

Android 的很多内核资源是按“单台设备”设计的：

- Binder 的物理页池、全局锁、Context Manager 都是单实例。
- 多个容器共享同一个驱动实例，一个容器的泄漏或高负载会影响其他容器。
- 容器之间的隔离主要靠命名空间与 cgroup，内核里的全局对象并不隔离。

所以共享内核方案要额外做压测与隔离，比如 binderfs 多实例、限制单容器的 Binder 使用量。

### 一次全容器故障的排查顺序

| 顺序 | 看什么 | 目的 |
|---|---|---|
| 1 | 影响范围 | 判断是宿主机、内核还是镜像 |
| 2 | 宿主机 dmesg | 找 panic/oops/watchdog/OOM |
| 3 | 容器 logcat/tombstone | 找应用或 native 崩溃 |
| 4 | pstore/last_kmsg | 找上次崩溃的现场 |
| 5 | Binder 状态 | 看共享驱动是否异常 |
| 6 | 资源与调度 | 看中断、内存、CPU、IO |

顺序的原则是“从共享层往容器层查”，因为共享层的故障会同时影响所有容器。

### 压测与故障是两件事

实习期间还做过一次主动压测：单台虚机开数十个容器，用测试应用制造 Binder 高负载，观察线程池与内存映射区是否达到极限，结论是没有出现容器或虚机崩溃。

压测回答的是“这套方案在设定压力下稳不稳”，故障回答的是“某次异常为什么发生”。两者不能互相替代：压测没崩，不代表不会出故障；出了故障，也不能反推压测无效。

### 结论边界

- 修复了现象，不等于定位了根因。
- 压测通过，不等于所有场景都安全。
- 共享内核的隔离，靠的是约束与监控，不是天然安全。

面试时把这三条说清，比硬编一个“根因是内核 bug”更可信。

# 接收维度：为什么用 DataChannel，而不是 AudioTrack 或 REMOTE_SUBMIX

## 问题

“远端音频怎么进到云手机？你们调研了哪些接收方案，为什么选这个？”

## 我的回答

我只讲了“系统混音会混音、二次播放有延迟”，没有把方案列表讲全，也没有说清 WebRTC AudioTrack 与 DataChannel 的关系。

## 参考答案

接收侧调研了四个方案：

- REMOTE_SUBMIX：录系统播放的声音。
- WebRTC AudioTrack：在 WebRTC 解码输出点直接取 PCM。
- DataChannel：前端把 PCM 切片，封装成自定义协议发到代理端。
- HTTP/2 或 gRPC：把音频流注入代理端。

最终选择 AudioTrack 优先、DataChannel 兜底；实际落地时 AudioTrack 路径没有走通，保留 DataChannel。

## 相关知识点

### 四个方案

| 方案 | 数据形态 | 延迟 | 兼容性 | 带宽 | 工程成本 |
|---|---|---|---|---|---|
| WebRTC AudioTrack | 解码后的 PCM | 低 | 中 | 低 | 中高 |
| WebRTC DataChannel | 切片 PCM，自定义协议 | 中 | 高 | 高 | 中 |
| HTTP/2 / gRPC | PCM 或 Opus | 中高 | 高 | 中 | 中高 |
| REMOTE_SUBMIX | 系统混音后的 PCM | 不适用 | 低 | 低 | 低 |

### REMOTE_SUBMIX 为什么不行

REMOTE_SUBMIX 采集的是系统播放的声音：

- 多个音源同时播放时，采到的是混音结果，无法分离。
- 需要先播放再采集，播放与采集各有缓冲，延迟叠加。
- 扬声器与麦克风同时工作，可能产生回声，需要额外的回声消除。

如果只是“让应用听到远端声音”，播放加采集够用；但目标是“让远端声音变成麦克风输入”，虚拟设备更合适。

### AudioTrack 为什么没走通

WebRTC 的远端音轨是否支持 addSink/setSink，取决于构建配置与版本。我做过反射探测，也挂过 InvocationHandler，但最终只保留 DataChannel 路径。

原因不是 DataChannel 更好，而是 AudioTrack 依赖 WebRTC 内部接口，设备、ROM、SDK 版本一变就可能失效，维护成本高。DataChannel 虽然带宽开销大，但协议在自己手里，问题可定位。

### DataChannel 的协议演进

早期用 JSON 加 Base64 传输 PCM，问题很明显：

- Base64 让体积膨胀约三分之一。
- JSON 解析增加 CPU 开销。
- 长流媒体下带宽与延迟都吃亏。

后来改成自定义二进制协议：固定前缀加头部，头部包含序列号、时间戳、采样率、声道、格式、载荷长度，后面跟 PCM。二进制协议让解析变简单，也方便做丢包检测与时间轴对齐。

### 为什么最终选 DataChannel

- 兼容性：不依赖 WebRTC 内部 sink 接口，换版本不容易失效。
- 可控性：协议、缓冲、重传策略都在自己手里。
- 可调试：消息边界清晰，抓包与日志都好定位。

代价是带宽与 CPU 开销高于 AudioTrack，弱网下需要自己做节流与丢包补偿。

### 技术栈

| 层 | 选型 |
|---|---|
| 传输 | WebRTC DataChannel |
| 协议 | 自定义二进制 PCM，固定头加载荷 |
| 代理端 | Java，解析、重排、补偿、增益 |
| 备选 | WebRTC AudioTrack（因依赖内部接口，最终未采用） |

# 转发维度：为什么用 LocalSocket，而不是共享内存或 Binder

## 问题

“代理端为什么用 Java？为什么用本地套接字，不用 Binder 或共享内存？”

## 我的回答

我说 Java 是为了复用实时通信的 SDK，本地套接字是因为实现简单，Binder 适合控制面不适合数据面。回答不够完整，没有讲共享内存的取舍。

## 参考答案

Java 的原因：

- 实时通信的 SDK 与业务逻辑多在 Java 侧，复用成本低。
- 代理端还要处理会话、信令、控制指令，Java 生态更合适。
- 音频处理是字节操作，Java 也能做，瓶颈不在语言。

本地套接字的原因：

- 数据面是连续的 PCM 流，套接字是流式接口，写读自然。
- 实现简单，连接、断开、写失败都容易观测。
- Binder 更适合方法调用与控制信息，传大块数据有拷贝与调度开销。
- 共享内存是更优解，但要自己做同步与生命周期，第一版先用套接字。

## 相关知识点

### 四个转发方案

| 方案 | 长流媒体 | 吞吐 | 调试 | 权限边界 | 复杂度 |
|---|---|---|---|---|---|
| LocalSocket | 中 | 中 | 高 | 高 | 低 |
| 共享内存 | 高 | 高 | 中低 | 中 | 高 |
| Binder/AIDL | 高 | 高 | 中 | 高 | 中高 |
| 纯 Binder 传数据 | 低 | 低中 | 中 | 高 | 中 |

### 套接字的代价

本地套接字不是零成本：

- 数据从用户态写入内核缓冲，再被另一端读出，多一次拷贝。
- 每次读写有系统调用与上下文切换。
- 内核缓冲有限，生产快于消费时会堆积，需要背压。

这些代价在单路音频、48kHz 单声道的量级下可以接受；多路或高码率时，共享内存更合适。

### 共享内存的代价

共享内存接近零拷贝，但：

- 要自己实现读写指针、同步、可见性。
- 要处理进程崩溃后的清理与死锁。
- 调试比套接字难，出问题不好抓。

所以第一版用套接字、稳定后再换共享内存，是合理的演进路径。

### Binder 为什么不适合数据面

Binder 的设计目标是跨进程方法调用：

- 每次调用有事务开销，适合控制信息。
- 数据要序列化，大块 PCM 会增加拷贝与 CPU。
- 同步调用会占用客户端线程，音频流是持续的，不适合每帧一次调用。

Binder 可以用来传控制参数、传共享内存的句柄，但数据本身走共享内存或套接字更合适。

### 技术栈

| 层 | 选型 |
|---|---|
| 进程间 | Unix domain socket（本地套接字） |
| 帧格式 | 头部加 PCM 载荷，头部含采样率、声道、长度等 |
| 代理端 | Java 写入，失败可重连 |
| 系统侧 | C++ 接收服务，解析后写环形缓冲 |

# 上行维度：为什么用进程内 HAL，而不是 Vendor HAL

## 问题

“为什么不用完整的 AIDL 或 HIDL HAL，而是做成进程内 HAL？”

## 我的回答

我说完整 HAL 改动大，进程内 HAL 数据不用多一次跨进程。回答方向对，但没有讲完整 HAL 到底包含什么，也没有讲进程内 HAL 的缺点。

## 参考答案

上行侧调研了两个方案：

- HAL 进程内虚拟设备：在 audioserver 内实现，App 无感，改造成本中等。
- Vendor 扩展虚拟设备：走标准 HAL 进程，标准化强，工程量大、迁移成本高。

最终选进程内 HAL：

- 好处：少一个进程、少一次跨进程通信、改动集中在音频模块、不用新增服务配置与权限策略。
- 代价：不符合 Treble 的进程隔离，HAL 崩溃会带崩 audioserver；不能给其他产品复用；大版本升级迁移成本高。

## 相关知识点

### 两个方案对比

| 方案 | App 无感 | 系统改造成本 | 可控性 | 迁移成本 |
|---|---|---|---|---|
| HAL 进程内虚拟设备 | 高 | 中 | 高 | 中 |
| Vendor 扩展虚拟设备 | 高 | 高 | 中高 | 高 |

### 完整 HAL 包含什么

一个完整的 AIDL HAL 不只是接口文件，还包括：

- 接口定义与版本声明。
- HAL 服务进程与可执行文件。
- init rc 里的服务定义与接口注册。
- VINTF manifest 里的实例与版本。
- SELinux 域、标签、访问规则。
- 构建规则与分区归属。

缺任何一项，framework 都可能找不到服务或拒绝访问。

### 进程内 HAL 怎么接进框架

- 在音频框架加载模块时，按模块名识别自定义模块。
- 不走 HAL 工厂，直接构造设备对象。
- 设备对象实现框架的 HAL 接口，提供输入流的读写。
- 策略层声明设备与模块，让路由能选中它。

这样框架的其他部分不需要知道它是“假的”还是“真的”，只按接口调用。

### 进程内 HAL 的风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 崩溃带崩 audioserver | 所有音频失效 | 异常保护、看门狗、快速重启 |
| 不符合 Treble | 升级迁移成本高 | 接口隔离、减少对框架私有结构的依赖 |
| 不可复用 | 其他产品要重写 | 设备实现与框架适配分层 |
| 难以测试 | 问题定位靠日志 | 指标、单元测试、模拟数据源 |

### 技术栈

| 层 | 选型 |
|---|---|
| 设备接口 | HAL 设备接口与输入流接口 |
| 加载方式 | 按模块名进程内构造，不走 HAL 工厂 |
| 策略 | audio policy XML 独立 module，输入源优先路由 |
| 采样率 | 设备侧固定 48kHz 单声道，录音线程按客户端请求重采样 |
| 缓冲 | 环形缓冲，写满按整帧丢旧，读取按实时速率对齐 |

# 抖动缓冲怎么设计

## 问题

“网络会乱序、丢包、抖动，你的缓冲怎么设计？参数怎么定？”

## 我的回答

我说按序号重排，缺包时等一会儿，等不到就补静音，积压多了丢旧的。参数记不清，只说“根据网络情况调整”。

## 参考答案

抖动缓冲做三件事：

- 按序号重排：用有序结构保存待播放帧，按序号取出。
- 等缺失包：缺包时等待一个窗口，窗口大小是延迟与乱序容忍的权衡。
- 控制积压：积压超过上限时丢弃旧帧，保证延迟不持续增长。

参数没有绝对最优，取决于网络与场景：

- 等待窗口：几个帧的时长，弱网可以适当加大。
- 补偿上限：避免长时间断流补出大量静音。
- 积压上限：超过就丢旧保新，实时性优先。

## 相关知识点

### 为什么用有序结构

乱序到达时，需要按序号取最小可用帧。有序结构的插入、删除、取最小都是对数复杂度；数组需要连续序号，中间插入要搬移；链表查找最小值是线性。

如果序号连续且范围有限，可以用环形数组加位图，效率更高，但要处理回绕与空洞。

### 等待窗口的权衡

窗口太小：

- 乱序包还没到就被判定丢失，补了静音，听感断续。
- 网络抖动稍大就频繁丢包。

窗口太大：

- 延迟增加，实时性变差。
- 积压风险上升，需要更激进的丢弃。

常见做法是固定窗口加动态调整：先用一个保守值，统计抖动后再调。

### 积压上限与丢帧策略

积压上限的作用是防止延迟无限增长。到达上限时，有两种策略：

- 丢最旧的帧：保证最新数据能播，延迟不增长，但会丢内容。
- 丢最新的帧：保证连续性，但延迟会增长，最终还是要丢。

实时音频通常选丢旧，因为旧数据已经过期。丢的时候要按整帧对齐，避免从半帧开始切出杂音。

### 指标怎么建

抖动缓冲的可观测指标：

- 收包数、字节数、丢包数。
- 等待窗口内的补帧数、超时补帧数。
- 当前积压帧数、积压时长。
- 丢弃原因分类计数。

有了这些指标，调参才有依据，而不是凭听感。

# 丢包补偿为什么用静音帧

## 问题

“丢包时为什么补静音，不做预测？补偿帧的时间戳怎么给？”

## 我的回答

我说静音帧简单，不会引入错误信号；时间戳用上一帧加一个帧时长。回答基本对，但没有讲预测的代价与时间戳错误的后果。

## 参考答案

静音帧的原因：

- 实现简单，不需要模型与历史数据。
- 不会产生伪音、啸叫等错误信号。
- 让上层持续有数据，避免欠载与时间轴断裂。

代价是听感上是静音，音乐场景可能不适用。预测算法（基音重复、LPC）能改善听感，但复杂度和误判风险更高。

时间戳的给法：

- 优先用上一帧时间加帧时长。
- 没有上一帧时，用本地时钟兜底。
- 补偿帧也要保持时间轴连续，不能跳变。

## 相关知识点

### 静音帧与舒适噪声

静音帧是全零 PCM，舒适噪声是低能量噪声。前者实现最简单，后者听感更自然，但需要生成噪声、控制能量。

对语音场景，静音帧通常够用；对音乐或长丢包，舒适噪声或预测更好。

### 时间戳错误的后果

补偿帧的时间戳如果乱给：

- 上层时间轴出现跳变，容器时长错误。
- 回声消除、音画同步的参考错位。
- 应用按时间戳拼接时出现空洞或重叠。

所以补偿帧不是“补上就行”，要补在正确的时间点上。

### 时间戳的来源

音频帧的时间戳可能来自：

- 发送端的时间轴（浏览器、采集设备）。
- 本地接收时间。
- 本地单调时钟。

跨进程传输时，要把发送端时间轴映射到本地时间轴，映射关系要稳定。补偿帧用的是映射后的本地时间，不是发送端时间。

# 时钟漂移怎么发现和补偿

## 问题

“两端时钟频率不一致会怎样？你怎么发现、怎么补？”

## 我的回答

我说会比较发送端时间增量和本地时间增量，偏差大了就裁剪缓冲。回答方向对，但没有讲漂移的成因、阈值怎么定、为什么按整帧裁。

## 参考答案

两端晶振频率有微小差异，长期运行会积累：

- 发送端快，接收端慢：缓冲越来越满，延迟增长。
- 发送端慢，接收端快：缓冲越来越空，出现欠载。

发现方法是比较“发送端时间增量”与“本地时钟增量”，偏差超过阈值就裁剪。裁剪要按整帧，因为音频帧是固定时长，裁半帧会破坏帧边界。偏差太大、无法整帧裁剪时，直接清空，避免半帧长期错位。

## 相关知识点

### 漂移与抖动的区别

- 抖动是短时间的时间偏差，表现为乱序、到达时间不均匀。
- 漂移是长时间的平均速率偏差，表现为缓冲缓慢变满或变空。

抖动靠缓冲吸收，漂移靠补偿。两者都会影响延迟，但处理方式不同。

### 阈值怎么定

阈值太大，漂移积累到明显才处理，延迟已经高了；阈值太小，频繁裁剪，听感抖动。

常见做法是取一个“人能感知但不明显”的范围，再结合缓冲深度。比如缓冲只有几百毫秒时，漂移阈值不能设得比缓冲还大，否则还没触发就欠载了。

### 为什么按整帧裁

PCM 帧是采样点的集合，时间戳按帧对齐。裁半帧意味着从某个采样点中间开始播，后续的时间戳、重采样、容器时长都会错位。

按整帧裁的代价是裁剪粒度较粗，但能保证时间轴连续。裁不了时清空，是为了避免半帧长期存在造成持续杂音。

### 漂移补偿的另一种思路

除了裁剪，还可以微调重采样比率：让本地重采样器稍微快一点或慢一点，慢慢把缓冲拉回目标水位。这种方式听感更平滑，但实现复杂，需要重采样器支持动态比率。

# AGC 怎么设计

## 问题

“音量大时爆音，音量小时听不清，你的增益控制怎么做的？参数怎么取？”

## 我的回答

我说按帧算峰值，把峰值往目标值靠，限制增益范围，攻击快释放慢。参数记不清，只说“调试出来的”。

## 参考答案

AGC 的基本流程：

- 按帧计算峰值或 RMS。
- 算目标增益，让峰值靠近目标。
- 限制增益范围，避免过度放大。
- 平滑增益变化，攻击快、释放慢。
- 末端软削波或限幅兜底。

参数取值的依据：

- 目标峰值留 6 到 8 dB 余量，避免削波。
- 增益范围限制在合理倍数，避免放大底噪。
- 攻击快，压住突发的爆音；释放慢，避免音量抽吸。
- 低能量帧加噪声门，限制增益上限。

## 相关知识点

### 峰值与 RMS

- 峰值是样本绝对值的最大值，反映瞬态。
- RMS 是均方根，反映平均能量。
- 两者结合，能兼顾爆音与响度。

只看峰值，会把短促的尖峰压得过狠；只看 RMS，可能漏掉瞬态爆音。

### 定点与浮点

音频处理常用定点，原因是：

- 嵌入式与移动端浮点开销与功耗更高。
- 定点结果确定，便于复现。
- 定点要注意溢出与精度，增益用 Q 格式表示。

浮点实现简单，适合原型与桌面环境；量产代码常见定点。

### 攻击与释放

攻击是增益下降的速度，释放是增益回升的速度：

- 攻击快，能及时压住爆音，但可能压掉瞬态。
- 释放慢，听感平滑，但可能长时间压着音量。

常见做法是攻击系数远大于释放系数，形成非对称平滑。

### 为什么还要末端限幅

AGC 之后仍可能超过满幅：

- 多帧叠加、重采样过冲。
- 增益变化瞬间的过冲。
- 上游数据本身已经接近满幅。

软削波或限幅在末端兜底，保证输出不超出范围。软削波比硬削波听感好，但会引入谐波。

# 环形缓冲的背压怎么做

## 问题

“代理侧写得快、录音线程读得慢，缓冲怎么处理？写满了怎么办？”

## 我的回答

我说写满就丢最旧的数据，积压多了就泄洪。回答对，但没有讲泄洪的粒度、读取对齐、欠载补帧。

## 参考答案

环形缓冲的背压分三个方向：

- 写满：按整帧丢弃最旧数据，保证新数据能进来。
- 积压：超过阈值时渐进泄洪，每次削一点，避免突然跳变。
- 欠载：读取时按实时速率对齐，读不到就补静音，避免上层阻塞。

## 相关知识点

### 为什么按整帧丢

和裁剪一样，按整帧丢能保持帧边界与时间戳对齐。丢半帧会让后续采样错位，产生杂音。

丢最旧而不是丢最新，是因为旧数据已经过期，保留最新数据对实时性更有价值。

### 渐进泄洪

一次性把积压削到目标，会造成明显的时间跳变。渐进泄洪每次削几毫秒，多次之后回到目标水位，听感更平滑。

代价是需要一个持续的处理循环，不能只在写满时触发。

### 读取速率对齐

录音线程按实时速率读取，不能读得太快或太慢：

- 读太快，缓冲很快空，频繁欠载。
- 读太慢，缓冲堆积，延迟增长。

对齐的方式是按时间戳或按周期读取，读不到时补静音，保证上层拿到稳定长度的数据。

### 缓冲深度的取舍

缓冲深，抗抖动能力强，但延迟高；缓冲浅，延迟低，但容易欠载。

常见做法是动态调整：网络好时浅一点，网络差时深一点。动态调整要有滞回，避免频繁切换。

# 某个应用录音时长异常怎么排查

## 问题

“你提到某个应用的录音时长不对，具体是什么问题、怎么定位的？”

## 我的回答

我说应用录出来的音轨时长和真实时间对不上，最后发现是采样率没对齐。回答太简略，没有讲排查过程与修复方式。

## 参考答案

现象：应用录出来的音轨，解析出的时长与真实时间轴不一致，听起来速度也不对。

排查：把链路拆开，逐段对账。

- 代理侧时间戳是否连续、是否与发送端一致。
- 系统侧写入的时间戳是否连续。
- 录音线程输出的采样率是否与客户端请求一致。
- 容器封装时声明的采样率与实际数据是否一致。

定位：客户端用固定采样率打开录音，系统侧按设备采样率输出，两边没有对齐，时间轴被拉伸。

修复：录音线程做重采样，设备侧保持固定采样率，客户端保持自己请求的采样率，中间由重采样器转换。这样设备只需要声明一种采样率，应用也不用改。

## 相关知识点

### 采样率不一致的后果

- 数据量不变，但播放速度变了，听起来变快或变慢。
- 容器声明的采样率与数据不一致，解析出的时长错误。
- 音画同步出问题，视频与音频对不上。

采样率是音频链路的“时间标尺”，任何一段不一致，最终产物都会错。

### 为什么设备侧固定采样率

设备侧固定采样率的好处：

- HAL 只需要声明一种配置，减少组合。
- 驱动与硬件只需要支持一种速率，降低复杂度。
- 上层按需重采样，兼容不同应用。

代价是重采样在录音线程里做，增加一点 CPU。对语音场景，这点开销可以接受。

### 重采样放在哪一层

重采样可以放在：

- 应用侧：应用自己做，兼容性差。
- 录音线程：系统统一做，应用无感。
- HAL：设备做，硬件依赖强。

选择录音线程，是因为它在系统内、对应用透明，且能拿到客户端请求的采样率。

### 怎么验证修复

- 用系统相机录像，检查音轨时长。
- 用目标应用录音，解析容器，比较时长与真实时间。
- 用 `ffprobe` 看采样率、声道、时长。
- 长录、短录、多次录，确认稳定。

# 音质问题为什么拖了一个月

## 问题

“你说音质问题拖了很久，为什么？最后怎么解决的？”

## 我的回答

我说早期方案音质差，试过改缓冲、改重采样、改增益，效果不稳定，最后回退过一次，后来定位到采样率对齐。回答真实，但没有讲“为什么难”和“怎么建指标”。

## 参考答案

难在两点：

- 跨层：音质受采集、编码、传输、缓冲、重采样、增益、播放多段影响，任何一段都可能出问题。
- 缺指标：早期只有零散日志，没有稳定口径，改一个参数不知道是变好还是变坏。

转折点是先建可观测性：把收包数、丢包原因、缓冲水位、欠载次数、削波次数固定下来，再逐项改。定位到采样率对齐后，问题才根治。

## 相关知识点

### 为什么先建指标

没有指标时，调参靠听感：

- 同一个人不同时间听感不同。
- 不同设备、不同内容差异大。
- 改一个参数，可能改善一个场景、恶化另一个场景。

有指标后，可以量化：

- 丢包率、欠载率、削波率。
- 缓冲水位、延迟分布。
- 增益平均值、峰值分布。

### 音质的常见来源

| 来源 | 现象 | 排查 |
|---|---|---|
| 采集 | 底噪、失真 | 换设备、看原始 PCM |
| 编码 | 金属音、模糊 | 换码率、换编码器 |
| 传输 | 断续、卡顿 | 看丢包、抖动、缓冲 |
| 重采样 | 高频损失、混叠 | 看滤波器、比率 |
| 增益 | 爆音、抽吸 | 看峰值、增益曲线 |
| 播放 | 破音、延迟 | 看 HAL、缓冲 |

### 回退是不是失败

回退不等于失败。当问题影响核心体验（音画不同步）时，先回退到稳定方案，再在新分支上继续定位，是工程上合理的选择。

关键是回退后要继续查，不能把回退当成结案。

# 如果重做会改什么

## 问题

“如果让你重做这条链路，你会改什么？”

## 我的回答

我说会用共享内存、加测试、加监控。回答方向对，但没有展开优先级与代价。

## 参考答案

按收益排序：

- 数据面换共享内存：减少拷贝与上下文切换，降低延迟。
- 端到端延迟打点：从采集到应用回调分段统计，替代“设计参数”。
- 自动化测试：覆盖缓冲边界、时钟漂移、采样率转换。
- 协议版本化：代理侧与系统侧解耦，升级不用同时改。
- 指标与告警：把临时日志变成长期指标。

## 相关知识点

### 共享内存的代价

共享内存不是免费的：

- 要自己实现读写指针、同步、可见性。
- 要处理进程崩溃后的清理。
- 调试比套接字难，出问题不好抓。

所以第一版用套接字、稳定后再换共享内存，是合理的演进路径。

### 端到端延迟怎么打点

在链路的几个关键点打时间戳：

- 远端采集时刻。
- 代理侧收到时刻。
- 写入系统时刻。
- 录音线程读出时刻。
- 应用回调时刻。

每段算差值，得到分段延迟。没有端到端数据，优化只能靠猜。

### 测试怎么补

音频链路的测试分三层：

- 单元测试：缓冲、重采样、增益的边界。
- 集成测试：代理侧到系统侧的协议、时间戳、采样率。
- 端到端测试：录音产物与真实时间的对齐。

测试数据可以用合成音频，覆盖静音、满幅、变频、丢包等场景。
